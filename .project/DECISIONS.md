## ADR-001 · 门户不拥有用户主数据管理权

- 日期：2026-09-17
- 状态：已确认
- 背景：统一门户需要承接统一登录后的访问入口，但用户注册和身份主数据已有上层平台负责。
- 决策：门户不建设独立用户主数据管理权；注册动作跳转至上层身份平台完成。门户需要使用用户信息时，以身份平台提供的数据为准。
- 原因：避免重复建设用户体系并防止多套身份数据产生冲突。
- 影响：用户管理公共模块在本项目中不作为独立 CRUD 启用；后续页面、接口和数据库设计不得把门户设计为用户主数据源。
- 替代方案：门户独立维护用户体系——不采用。

## ADR-002 · 门户权限与子系统权限分离

- 日期：2026-09-17
- 状态：已确认
- 背景：统一门户需要管理自身菜单、入口和门户功能权限，但 43 个子系统存在各自业务权限和开户规则。
- 决策：门户角色只管理门户自身权限；应用访问授权由各子系统负责；子系统开户由各子系统自行决定和处理。
- 原因：保持权限职责清晰，避免门户与子系统形成双重授权源。
- 影响：后续权限模型、操作矩阵和接口设计必须区分“门户权限”和“子系统权限”，不得由门户替代子系统完成内部授权。
- 替代方案：统一门户集中管理全部子系统权限——不采用。

## ADR-003 · 43 个子系统统一纳入应用与待办聚合

- 日期：2026-09-17
- 状态：已确认
- 背景：统一门户需要成为 43 个子系统的统一入口，并承载跨系统待办聚合。
- 决策：43 个子系统全部进入“全部应用”；43 个子系统待办全部接入门户聚合范围。
- 原因：保证统一门户具有完整的应用入口覆盖和统一待办入口。
- 影响：后续 P1/P2 需形成应用清单、待办接入清单、入口规则和异常/空态规则；P3 及接口阶段需定义应用与待办数据契约。
- 替代方案：仅接入部分重点子系统——当前基线不采用。

## ADR-017 · 门户管理员采用“用户类别 + 权限范围”模型

- 日期：2026-09-18
- 状态：已确认
- 决策：管理端统一以“门户管理员”作为用户类别；超级管理、应用管理、集成管理、公告管理、审计、身份映射等作为门户内部权限范围。一个门户管理员可以获得一个或多个权限范围。
- 影响：旧称“应用管理员、集成管理员、公告管理员、审计管理员、短信管理员”等不再作为独立用户类型；页面、流程、状态机和操作矩阵统一改用“门户管理员（XX权限）”。
- 数据影响：现有通用RBAC表结构无需变更；最终角色模板和权限码矩阵仍在P6冻结。

## ADR-018 · 上层公共服务优先，门户不重复建设认证载体与短信平台

- 日期：2026-09-18
- 状态：已确认方向 / 接入路径待外部资料
- 决策：二维码、手机验证码等认证载体及其有效期由上层身份平台提供；门户负责发起认证、展示状态、处理回调和建立Session。短信等公共服务优先复用上层平台，门户仅在最终确认需要时承担必要接入或转接。
- 影响：删除短信费用统计；不固定建设短信渠道、短信模板审批、费用核算和独立短信管理员。现有P3 `sms_*` 结构暂作为条件预留，后续根据上层接入方案收敛。
- 与历史决策关系：本ADR对ADR-006“门户统一提供短信服务能力”进行收敛和替代；ADR-006不再作为当前执行口径。

## ADR-020 · 门户增加本地身份来源，但不建设面向社会用户的第三套身份中心

- 日期：2026-09-20
- 状态：当前执行
- 背景：门户维护人员不一定拥有闽政通或闽政务账号。如果管理端强依赖外部身份源，部署、初始化和运维存在不可用风险。
- 决策：增加 `PORTAL_LOCAL → LOCAL / 门户本地用户`。本地用户由门户维护账号和密码凭证，第一阶段主要用于管理端。
- 限制：
  - 不开放公众自助注册本地账号；
  - 本地用户不自动获得管理员权限；
  - 必须通过门户角色决定能否进入管理端；
  - 外部CITIZEN/GOV权威身份资料仍不得由门户修改；
  - 本地账号不用于替代闽政通/闽政务面向公众和政务人员的身份体系。
- 安全要求：密码Hash保存、首次改密、失败锁定、超级管理员重置/解锁、登录与安全操作审计；首个超级管理员明文密码不得写入源码或Git。
- 与历史决策关系：
  - 对ADR-001“门户完全不采用独立用户体系”的绝对表述进行收敛：门户仍不建设外部用户主数据中心，但允许维护**门户自身LOCAL身份**。
  - 对ADR-019“门户不维护密码”的表述进行收敛：该限制继续适用于闽政通/闽政务用户；LOCAL密码由门户负责。

## ADR-021 · 默认管理角色收敛为超级管理员与门户管理员

- 日期：2026-09-20
- 状态：当前执行
- 背景：实际门户预计只有1～2名维护人员，预置应用、集成、公告、审计、映射等多个角色会造成不必要的授权复杂度。
- 决策：默认只Seed两个角色：
  - `SUPER_ADMIN`：门户超级管理员；
  - `PORTAL_ADMIN`：门户管理员。
- 权限实现：继续保留 `MENU / PAGE / ACTION` RBAC。未来确有分工时允许创建自定义角色。
- 数据范围：第一阶段两个默认角色均按 `ALL_PORTAL`；`ORG / ORG_AND_CHILDREN / ASSIGNED_APPS` 等细粒度范围不作为P0页面建设重点。
- 高风险能力：本地管理员创建/密码重置、角色权限配置、超级管理员授权、关键系统配置等默认仅SUPER_ADMIN。
- 与历史决策关系：
  - ADR-017“门户管理员+多个权限范围”仍保留RBAC思想，但当前预置角色与首期实现按本ADR进一步简化。
  - 细分管理员称谓不作为首期默认角色。

## ADR-022 · 子系统账号关联采用“候选匹配 + 二次验证”，高风险账号进入审核

- 日期：2026-09-20
- 状态：当前执行
- 背景：纳管子系统技术条件不一致，部分系统缺少与闽政通/闽政务一致的稳定人员唯一标识。仅使用姓名+手机号直接绑定存在误关联风险。
- 决策：
  - BIND场景继续采用 AUTO / SELF / REVIEW / ADMIN；
  - 有可信稳定唯一标识且唯一匹配时允许AUTO；
  - 无稳定ID时，姓名+已登记手机号、姓名+工号等只用于发现候选账号；
  - 候选账号必须通过子系统跳转认证、子系统原登记手机号OTP、上层重新认证、子系统账号一次性认证或管理员审核完成二次验证；
  - 普通账号验证通过可BOUND；高权限/风险账号可进入REVIEWING；
  - 同一 application_id + external_user_id 只能有一个有效BOUND；已绑定其它统一用户时禁止自动覆盖，转CONFLICT；
  - 子系统账号状态和映射状态分离；
  - 解绑、重绑、审核、冲突处理必须审计。
- 安全要求：
  - 门户不保存子系统明文密码、OTP或Token；
  - OTP必须发送到子系统原账号已登记手机号，用户现场新填手机号不能单独作为账号所有权证明。
- 跨身份源补充：
  - CITIZEN/GOV未来如需要合并，不得仅凭姓名+手机号自动合并；
  - 稳定权威跨源ID优先；
  - 无稳定ID时采用候选匹配+上层重新认证/更强实名核验；
  - 如需人脸核验，优先调用权威身份平台能力，门户不自行保存人脸模板。
- 影响：登录与用户体系、业务流程、功能清单、页面规格、字段规则、范围边界、状态机、Service契约、数据设计/字典、操作矩阵及0.3.0整改计划同步本决策。
