## 2. 建设背景与目标

卫健统一门户用于在闽政通、闽政务等上层权威身份体系与多个卫健业务子系统之间建立统一访问入口。

建设目标：

- 提供统一登录入口；
- 承接闽政通、闽政务两类外部访问身份，并建立独立的门户管理用户授权体系；
- 建立统一用户索引，但不重复建设完整公众/政务身份库；
- 聚合用户可访问的业务应用；
- 支持应用入口申请、账号确认及访问前校验；
- 聚合待办、消息和门户公告；
- 为管理员提供应用、用户、角色、组织、字典、映射、配置、日志及接入健康管理；
- 保持门户入口权限与子系统业务权限严格分离；
- 为各业务子系统提供统一 SSO / TODO / MESSAGE 接入规范；
- 形成业务闭环完整、可持续接入业务子系统的统一门户能力。

## 3. 系统定位

### 3.1 总体关系

```text
闽政通 ──→ 公众用户 CITIZEN ┐
闽政务 ──→ 政务用户 GOV    ├─→ 门户访问主体 ─→ 用户端/业务子系统
                                 │
门户管理用户（独立授权主体） ───┴─→ 管理端
  ├─ 可绑定闽政通/闽政务身份
  └─ 可使用门户本地管理账号
```

卫健统一门户位于身份来源与业务子系统之间，承担“统一身份承接 + 门户入口授权 + 应用聚合 + 公共事务聚合 + 管理支撑”。

### 3.2 门户不是

门户不是：

- 闽政通/闽政务的替代身份平台；
- 子系统统一用户主库；
- 子系统统一角色中心；
- 子系统统一菜单权限中心；
- 子系统统一数据权限中心；
- 子系统业务审批平台；
- 复杂 APM、服务器监控或链路追踪平台。

### 3.3 总体原则

> 统一身份承接 + 门户入口授权 + 子系统分布式业务授权。

门户决定“用户能否从门户看到、申请、进入某个应用”，子系统决定“用户进入后拥有什么业务角色、菜单、数据和操作权限”。

## 4. 建设范围与责任边界

### 4.1 上层身份平台负责

闽政通负责公众用户权威身份，闽政务负责政务用户权威身份。

上层平台负责：

- 正式身份注册/开通；
- 实名认证；
- 外部账号安全；
- 外部身份核心状态；
- 扫码、手机号验证码等上层认证能力；
- 手机号登录所需的安全识别、风险控制、动态验证码发送、验证码有效期、重发间隔、频率限制和验证码校验；
- 短信验证码发送能力及短信通道由闽政通、闽政务或其统一短信服务提供；
- 如具备条件，可提供人脸等强身份核验能力。

门户不自行保存公众/政务用户人脸模板。

### 4.2 统一门户负责

门户负责：

- 统一登录入口；
- 闽政通/闽政务认证结果承接；
- 独立门户管理用户及门户本地管理账号认证；
- Portal Session；
- 统一用户索引；
- 用户类别识别；
- 门户访问主体状态与门户管理用户启用状态；
- 门户角色和 MENU / PAGE / ACTION 权限；
- 本地管理账号生命周期；
- 应用目录；
- 应用适用用户规则；
- DIRECT / BIND / REQUEST 入口模式；
- 应用访问申请；
- 应用入口授权；
- 子系统账号映射；
- 映射审核、异常和冲突处理；
- 待办、消息聚合；
- 门户公告；
- 组织索引；
- 字典与配置；
- SSO / TODO / MESSAGE 接入配置；
- 接入健康查看；
- 登录、访问、操作、接口、异常日志。

### 4.3 业务子系统负责

子系统负责：

- 子系统账号本体；
- 子系统开户注册；
- 子系统账号启停；
- 子系统业务角色；
- 子系统菜单权限；
- 子系统数据权限；
- 子系统业务审批；
- 业务状态；
- 高权限账号管理；
- 子系统自身认证/授权页；
- 子系统已有账号真实性；
- 子系统原登记手机号 OTP 或账号校验接口（如提供）。

### 4.4 首期不纳入范围

首期不建设：

- 公众用户完整生命周期管理；
- 政务人员完整生命周期管理；
- 外部用户密码管理；
- 面向公众开放门户本地管理账号自助注册；
- 子系统业务角色统一维护；
- 子系统菜单/数据权限集中维护；
- 门户替子系统直接创建业务账号；
- 复杂组织数据权限；
- 复杂应用级数据范围；
- 收藏应用；
- 复杂运维 APM；
- 短信费用统计。

## 5. 核心术语

| 术语 | 含义 |
|---|---|
| 身份来源 | MINZHENGTONG / MINZHENGWU（用户端外部身份） |
| 用户类别 | CITIZEN / GOV（用户端访问类别） |
| 门户角色 | SUPER_ADMIN / PORTAL_ADMIN / 后续自定义门户角色 |
| Portal Session | 统一门户登录后的会话 |
| 应用入口资格 | 用户是否可从统一门户进入某应用 |
| 子系统业务权限 | 用户进入子系统后由子系统判定的业务权限 |
| DIRECT | 满足适用范围后无需门户账号映射即可进入 |
| BIND | 进入前需要确认统一用户与子系统账号关系 |
| REQUEST | 进入前需要先取得门户应用入口资格 |
| BOUND | 子系统账号映射已有效确认 |
| TODO | 子系统推送至门户的待办 |
| MESSAGE | 子系统或门户产生的消息 |
| SSO | 门户到子系统的单点/统一跳转能力 |

## 6. 外部身份、门户访问主体与门户管理用户

三者必须严格分离。

### 6.1 外部身份与用户类别

| 身份来源 | 用户类别 | 权威主体 | 首期主要入口 |
|---|---|---|---|
| MINZHENGTONG / 闽政通 | CITIZEN / 公众用户 | 闽政通 | 用户端 |
| MINZHENGWU / 闽政务 | GOV / 政务用户 | 闽政务 | 用户端 |

规则：

- 身份来源不是门户角色；
- 用户类别不是门户角色；
- 门户不建设公众/政务用户完整身份生命周期；
- 权威姓名、账号、手机号等外部主数据不可由门户任意修改。

### 6.2 门户访问主体

门户为用户端保存最小必要统一索引，用于 Portal Session、待办、消息、全部应用、账号映射和审计。

现有 `unified_user` 在目标设计中继续承担这一职责，但只表示 CITIZEN/GOV 门户访问主体，不再承载本地管理账号。

### 6.3 门户管理用户

管理端使用独立 `portal_admin_user` 授权主体。

门户管理用户可以：

- 绑定一个闽政通/闽政务门户访问主体；
- 或使用门户本地管理账号认证。

是否可以进入管理端，由 `portal_admin_user.enabled + portal_role + portal_permission` 决定，不由用户类别自动决定。

### 6.4 跨身份源关系

CITIZEN 与 GOV 不默认自动合并。若未来需要跨源关联，应优先使用稳定权威跨源ID；没有稳定ID时采用候选匹配 + 上层重新认证/更强身份核验，不得仅凭姓名+手机号自动合并。

## 7. 门户管理用户与本地管理账号

### 7.1 门户管理用户

管理端“用户管理”管理的是门户管理用户，不是所有访问过门户的公众/政务用户。

管理用户至少包含：

- 管理用户ID；
- 展示账号/姓名；
- 认证类型：EXTERNAL / LOCAL；
- 外部访问主体绑定（EXTERNAL时）；
- 启用状态；
- 门户角色；
- 最近登录时间。

停用门户管理用户只取消管理端访问资格，不影响其上层闽政通/闽政务账号，也不影响其仍满足条件时使用用户端。

### 7.2 本地管理账号

本地账号用于初始化、运维或没有上层身份的管理人员。

本地管理账号直接属于 portal_admin_user，不再建立 LOCAL 普通访问用户。

本地凭证单独维护：

- username；
- password_hash；
- password_algorithm；
- must_change_password；
- failed_login_count；
- locked_until；
- password_updated_at；
- last_login_at。

规则：

- 不开放公众自助注册；
- 密码必须安全哈希；
- 明文密码、OTP、Token 不进入普通日志；
- 本地账号不自动等于管理员，仍必须分配有效门户角色；
- 最后一个有效超级管理员必须受后端事务保护。

### 7.3 外部身份管理员

闽政通/闽政务用户可以被授予管理资格。授权时仅建立 portal_admin_user 与访问主体的绑定，不复制成“本地用户”，也不改变其原用户类别。

## 8. 门户角色与权限模型

### 8.1 默认角色

首期只预置：

| 角色 | 编码 | 定位 |
|---|---|---|
| 门户超级管理员 | SUPER_ADMIN | 最高门户管理权限 |
| 门户管理员 | PORTAL_ADMIN | 日常门户维护 |

预计实际维护人员较少，因此首期不预置应用管理员、公告管理员、审计管理员、集成管理员等大量细分角色。

### 8.2 权限模型

门户 RBAC 支持：

```text
菜单 MENU
  └─ 页面 PAGE
       └─ 操作 ACTION
```

首期两个默认管理角色数据范围按 ALL_PORTAL 处理。

SELF / ORG / ORG_AND_CHILDREN / ASSIGNED_APPS 等数据范围作为后续扩展，不作为首期复杂配置项。

### 8.3 超级管理员

默认拥有：

- 全部管理端菜单；
- 全部页面；
- 全部操作；
- 用户及本地账号管理；
- 角色权限管理；
- 组织、字典、配置；
- 应用、公告、映射、监控、日志；
- 管理员授权；
- 本地用户密码重置；
- 关键配置维护。

系统必须保护最后一个有效超级管理员账号和超级管理权限。

### 8.4 门户管理员

默认承担日常维护：

- 管理首页；
- 通知公告；
- 应用目录；
- 应用访问申请；
- 子系统账号开通申请状态（如启用）；
- 运行监控；
- 身份与子系统映射；
- 用户查询及必要门户侧维护；
- 组织；
- 字典；
- 日志审计。

高风险操作可只允许超级管理员：

- 创建/删除本地管理账号；
- 重置其他管理员密码；
- 角色权限配置；
- 超级管理员授权；
- 删除关键配置。

### 8.5 子系统权限隔离

门户角色不得：

- 创建子系统业务角色；
- 修改子系统业务角色；
- 分配子系统菜单；
- 分配子系统数据权限；
- 代替子系统完成业务审批。

## 9. 用户端与管理端关系

“用户端”和“平台管理端”是两个使用入口，不是两个用户类别。

### 9.1 用户端

首期主要面向：

- CITIZEN；
- GOV。

### 9.2 管理端

进入管理端必须拥有有效门户管理角色。

管理端访问主体统一为门户管理用户。门户管理用户可绑定闽政通/闽政务访问主体，也可使用门户本地管理账号；是否能进入管理端由有效 portal_admin_user 与门户角色共同决定。

### 9.3 端切换

同一 Portal Session 下，若当前用户同时具备用户端和管理端访问资格，可提供“用户端门户 / 平台管理端”切换，不要求重复登录。

## 10. 信息架构与菜单

### 10.1 用户端门户

当前用户端左侧导航采用单层菜单，不再显示“个人事务”等额外一级分组标题。

```text
用户端门户
├─ 首页
├─ 待办事项
├─ 消息中心
├─ 通知公告
├─ 全部应用
├─ 我的申请
└─ 个人中心
```

菜单与页面关系：

- 首页 → `/portal/home`；
- 待办事项 → `/portal/todos`；
- 消息中心 → `/portal/messages`；
- 通知公告 → `/portal/announcements`；
- 全部应用 → `/portal/apps/all`；
- 我的申请 → `/portal/applications`；
- 个人中心 → `/portal/profile`。

补充规则：

- “全部应用”在左侧菜单中只显示一个入口；
- “我的应用 / 其它应用”属于全部应用页面内部的数据分组，不作为左侧子菜单；
- `/portal/apps/mine` 仅保留兼容隐藏路由，不作为当前用户端菜单入口；
- 公告详情、消息详情等详情页面不单独占用左侧菜单项，进入详情后保持对应业务菜单上下文；
- 用户端左侧菜单显示顺序以本节为当前需求基线。

### 10.2 平台管理端

```text
平台管理端

工作台
├─ 管理首页
└─ 通知公告管理

应用管理
├─ 应用列表
├─ 应用访问申请
├─ 子系统账号开通申请
└─ 运行监控

系统管理
├─ 用户管理
├─ 角色管理
├─ 组织管理
├─ 字典管理
├─ 身份与子系统映射
└─ 配置管理

日志审计
├─ 登录/认证日志
├─ 应用访问日志
├─ 门户操作日志
├─ 接口调用日志
└─ 异常日志
```

说明：

- “系统分类”并入字典管理；

- 不恢复“业务集成”一级菜单；
- 本地账号管理并入用户管理；
- 身份与子系统映射纳入系统管理。

## 11. 统一登录

### 11.1 路由

统一登录路由：`/login`。用户端和管理端共用同一个登录页。

### 11.2 登录身份入口

登录页提供三类登录入口，身份和管理授权分别处理：

- 公众用户：闽政通身份来源，用户类别为 `CITIZEN`；
- 政务用户：闽政务身份来源，用户类别为 `GOV`；
- 门户管理用户：可采用上层身份授权或门户本地管理账号登录，登录后须具备有效门户管理角色。

### 11.3 公众与政务用户登录

- 根据上层身份平台支持的能力展示扫码、手机号验证码等认证入口，扫码应具有有效期、失效和刷新规则；
- 手机号、验证码及安全验证仅在适用认证方式下显示，并按权威身份平台规则校验；
- 首次认证通过后建立门户访问会话，并据用户类别、适用范围及访问资格展示授权页面；
- “注册”“忘记密码”等操作跳转至对应上层身份平台，由权威服务办理；
- 门户不得自行保存上层认证密码、短信验证码或生物识别模板。

### 11.4 管理账号登录

- 管理账号登录提供账号、密码及按安全策略要求的验证码或风险核验；
- 本地管理账号由门户进行凭证校验与安全控制，外部管理用户先由对应上层身份平台完成认证；
- 通过认证后，仍须校验门户管理用户的启用状态、有效角色及授权范围；
- 登录失败、账号锁定、停用、权限不足时给出对应处理提示，不应直接进入管理端。

### 11.5 身份语义

- 公众访问主体：`MINZHENGTONG / CITIZEN`；
- 政务访问主体：`MINZHENGWU / GOV`；
- 门户本地管理认证方式：`PORTAL_LOCAL`，对应门户管理用户；
- 管理角色和外部用户类别相互独立，不得以用户类别推导管理权限。

### 11.6 门户会话

身份验证成功后建立门户会话，支持有效期、退出及失效处理：

- 公众/政务用户进入 `/portal/home`；
- 有权限的管理用户进入 `/admin/home`；
- 会话失效或权限被收回时应按权限边界退出或重新认证。

### 14.1.1 归属子系统与展示视图

本节的“归属子系统”查询条件及视图切换仅适用于 PC 公众门户 `/portal/apps/all`；移动端 `/m/apps` 继续使用现有关键词搜索和应用分类侧栏，不在头部增加归属子系统查询或视图切换按钮。

“全部应用”提供两个一体式分段切换选项：“按开通情况”（默认，对应“我的应用 / 其它应用”两个分组）和“按所属系统”（对应归属子系统分组），不新增左侧菜单。两种视图读取同一份当前用户可见应用结果，遵守相同的适用用户、授权及启停规则；切换视图不改变应用的访问资格、操作和数量。按子系统视图先按归属分组，再展示组内应用；历史或异常数据中未配置归属的应用单独列为“未归属”，不得猜测归到 7 组之一。

查询条件在现有应用名称/编码关键词、系统分类之外增加“归属子系统”。多个条件同时选择时取交集；两种视图共用查询结果，清空条件后恢复当前用户可见应用。组内卡片将归属子系统名称显示为灰色 TDesign 标签（字号 12px，与系统分类标签同一行），避免把归属子系统误写成系统分类。应用名称和两个标签均为单行显示；每个标签宽度优先按文字自然适应，仅当两个标签总宽度超过卡片内部可用空间时压缩并使用 `...` 省略，不允许标签超出卡片边界或换行。Tooltip 只在文字实际发生截断时显示完整名称，未截断时不触发。

**PC 页面布局规则**：查询条件、重置按钮与“按开通情况 / 按所属系统”分段切换组件处于同一查询工具栏；查询控件靠左，切换组件靠右。采用胶囊状一体式分段切换：整体及未选中项为白色背景、深色文字，选中项为系统蓝色背景和白色文字，外围使用统一细边框和圆角；窄屏空间不足时允许查询工具栏换行，分段切换本身不拆开。切换不清空当前查询条件。

**卡片展示规则**：上述两种视图的每个应用分组均直接渲染当前查询条件下的全部应用卡片，分组标题继续显示对应数量；不显示组内分页、每页条数选择和页码跳转，也不做组内 20 条截取。本规则仅针对 PC 公众端“全部应用”卡片分组，不扩展至公告、管理端表格、首页快捷应用或移动端列表。

### 14.2 内部访问模式

门户内部支持三种应用入口模式：

| 模式代码 | 中文名称 | 核心含义 | 用户侧主要表现 |
|---|---|---|---|
| DIRECT | 直接进入 | 用户满足应用启用、适用用户范围和入口可用等基础条件后，无需额外提交门户访问申请，也无需先建立子系统账号映射，即可直接进入后续 SSO / 应用跳转流程。 | 进入应用 |
| BIND | 账号关联后进入 | 用户进入应用前，需要先确认当前门户统一身份与目标子系统账号之间的对应关系；关联完成且账号可用后，才能继续进入目标应用。 | 申请使用 / 查看进度 / 进入应用 |
| REQUEST | 申请通过后进入 | 用户进入应用前，需要先提交门户应用访问申请；审核通过后取得门户入口资格，再根据该应用配置决定直接进入，或继续完成子系统账号关联。 | 申请使用 / 查看申请 / 完成账号确认 / 进入应用 |

三种模式分别解决不同问题：

- DIRECT：表示用户不需要经过额外申请或账号关联即可进入应用；
- BIND：解决“当前门户身份对应哪个子系统账号”的问题；
- REQUEST：解决“当前用户是否具备从门户进入该应用的入口资格”的问题。

补充规则：

- REQUEST 审核通过只代表取得门户入口资格，不代表获得目标子系统内部业务角色、菜单或数据权限；
- REQUEST 可以配置审核通过后进入 DIRECT 或继续进入 BIND；
- BIND 只管理门户统一身份与子系统账号的映射关系，不替代子系统自身的账号、角色和权限管理；
- 以上代码属于门户内部访问控制模型，普通用户页面不直接展示 DIRECT / BIND / REQUEST；“其它应用”卡片的初始主操作统一采用“申请使用”，进入后续流程后再根据实际结果显示账号确认、查看进度、查看原因等业务化操作。

### 14.3 DIRECT

满足：

- 应用已启用；
- 用户类别适用；
- 应用入口允许；

即可直接进入后续 SSO/跳转。

### 14.4 REQUEST

REQUEST 用于控制门户入口资格。

状态：

- PENDING（待审核）；
- APPROVED（已通过）；
- REJECTED（已驳回）；
- WITHDRAWN（已撤回）；
- EXPIRED（已失效）。

申请通过只代表“获得门户入口资格”，不代表获得子系统业务权限。

### 14.5 BIND

BIND 内部支持：

- AUTO；
- SELF；
- REVIEW；
- ADMIN。

用户侧不显示这些代码。

### 14.6 用户侧结果导向交互

用户侧以“当前结果 + 下一步操作”为核心。

可见操作收敛为：

- 进入应用；
- 申请使用；
- 完成账号确认；
- 查看申请；
- 查看进度；
- 继续处理；
- 查看原因；
- 重新处理。

可见状态使用业务化文案：

- 待申请；
- 申请处理中；
- 申请未通过；
- 需确认账号；
- 待继续处理；
- 处理中；
- 处理失败；
- 账号异常；
- 账号不可用。

不得直接把 BIND、VERIFYING、REVIEWING、CONFLICT 等代码暴露给普通用户。

“其它应用”卡片展示规则：

- 第一行显示应用名称；
- 第二行显示应用类型；
- 第三行单独显示当前状态和下一步操作，避免与应用类型挤在同一行；
- 对尚未具备使用条件、需要进入账号处理流程的应用，卡片初始主操作统一显示“申请使用”，不直接显示“完成账号确认”；
- 点击“申请使用”后，再根据实际情况进入门户访问申请、账号确认、开户注册或其它后续处理流程；
- “账号异常 / 查看原因”“处理失败 / 重新处理”“申请处理中 / 查看申请”等状态与操作必须在独立结果行中展示。

### 14.7 已有历史账号

当需要历史账号、密码、验证码或子系统自身认证时：

1. 门户先判断是否已有有效映射；
2. 如可通过可信唯一标识唯一确认，可在后台直接完成；
3. 如需用户认证，门户显示“需要完成账号确认”；
4. 用户点击“前往子系统确认”；
5. 历史账号、密码、验证码等在目标子系统输入；
6. 门户不采集这些凭据；
7. 用户完成后返回门户；
8. 门户通过回调/标准接口/重新检测更新结果。

### 14.8 未检测到子系统账号

显示：

> 需要开通账号。

默认操作：

- 前往子系统开通；
- 完成后重新检测。

规则：

- 门户不直接创建子系统账号；
- 开户规则由子系统决定；
- 只有子系统提供标准开户申请接口时，门户才可承接申请提交与状态回显。

### 14.9 高权限账号

高权限账号可在完成必要确认后进入 REVIEWING，待门户管理员审核。

用户侧只显示“处理中/账号确认已提交”。

### 14.10 冲突和失败

至少区分：

- ACCOUNT_NOT_FOUND（未找到账号）；
- INVALID_CREDENTIALS（账号凭证错误）；
- OTP_INVALID（验证码错误）；
- OTP_EXPIRED（验证码已过期）；
- ACCOUNT_DISABLED（账号已停用）；
- ACCOUNT_ALREADY_BOUND（账号已被关联）；
- MULTIPLE_CANDIDATES（存在多个候选账号）；
- REVIEW_REQUIRED（需要管理员审核）；
- UPSTREAM_UNAVAILABLE（上游服务不可用）；
- ACCOUNT_MAPPING_CONFLICT（账号映射冲突）。

不得将所有错误统一写成“关联失败”。

### 14.11 唯一绑定

同一 application_id + external_user_id 同时最多存在一个有效 BOUND 映射。

已绑定其他统一用户时：

- 不得自动覆盖；
- 进入 CONFLICT；
- 由管理员核实处理；
- 处理过程写审计。

## 20. 管理首页

路由：`/admin/home`。

面向有门户管理角色的用户，定位为“门户管理工作台”。首页主要回答四类问题：当前纳管规模、当前待处理事项、接入服务是否正常、最近有哪些接入异常。

### 20.1 顶部概览指标

顶部只保留四个同层级核心指标：

| 指标 | 统计口径 | 点击去向 |
|---|---|---|
| 纳管应用 | 当前统一应用目录中的应用总数 | 应用列表 |
| 启用应用 | 当前启用状态的应用数量 | 应用列表 |
| 门户访问用户 | 已建立门户访问主体索引的用户数量 | 门户访问主体 |
| 接入异常应用 | 应用列表中“综合运行状态=异常”的应用数量，同一应用仅计一次 | 运行监控 |

展示信息规则：

- 每个指标展示指标名称和统计值；
- 不重复展示“统一应用目录、当前启用、已建立统一用户索引、已配置服务运行异常”等非必要辅助说明。

业务规则：

- 不再显示“正常应用 / 异常应用”综合指标；
- 应用列表展示综合运行状态；应用停用优先显示“停用”，否则 SSO 始终为必需能力，已启用的 TODO / MESSAGE 也属于必需能力；必需能力中“异常、停用、未配置”依次优先，全部正常才显示“正常”；
- 顶部“接入异常应用”按上述综合状态为“异常”的应用去重计数；右侧“接入异常”明细仍按服务逐条展示，一个应用可出现多条；
- 综合状态为“未配置 / 停用”的应用不计入顶部异常应用数。

### 20.2 待处理事项与常用管理

“待处理事项”和“常用管理”在常规桌面宽度下同一行展示：

- 左侧“待处理事项”为主要区域，宽度大于右侧；
- 右侧“常用管理”为快捷入口区域；
- 两个区块标题只显示标题本身，不再显示“按当前账号权限显示”“快速进入常用管理模块”等辅助提示；
- 窄屏时允许自动上下堆叠。

待处理事项包括：

- 应用访问申请；
- 账号开通申请；
- 账号确认审核；
- 映射异常；
- 异常日志；
- 待发布公告。

待处理事项规则：

- 展示各类待处理数量；
- 点击后进入对应管理页面。

常用管理规则：

- 公告快捷入口为“新增公告”，点击后进入通知公告管理并直接发起新增公告；
- 其他主要入口包括应用列表、用户管理、身份与子系统映射；
- 顶部概览不重复展示“待审核申请”，避免与待处理事项重复。

### 20.3 接入运行状态与接入异常

“接入运行状态”和“接入异常”在常规桌面宽度下同一行展示：

- 左侧：接入运行状态；
- 右侧：接入异常；
- 窄屏时自动上下堆叠。

接入运行状态按 SSO / TODO / MESSAGE 三行纵向展示，每行分别显示：

- 正常；
- 异常；
- 未配置/停用。

该区域只承担接入健康摘要，点击进入运行监控查看应用级明细。

### 20.4 接入异常

展示最近的异常接入服务，按最近检测时间近到远排序。

每条至少显示：

- 应用名称；
- 接入服务类型；
- 最近错误摘要；
- 异常状态。

同一应用如果 SSO / TODO / MESSAGE 中有多个服务异常，应按服务分别计数和展示。

映射冲突、身份异常等业务异常不混入本区域，统一进入“待处理事项”或对应业务管理页面。

无异常时显示“暂无接入异常”。

### 20.5 页面位置与响应式

- 常用管理不再固定放置在页面底部，而是与待处理事项同一行；
- 接入运行状态、接入异常继续位于该行之后；
- 常用管理按当前账号权限动态显示，不替代左侧正式菜单；
- 桌面宽度不足时，“待处理事项 / 常用管理”自动上下排列；
- 管理首页不建设复杂运行监控图表，不展示服务器资源、链路追踪等 APM 信息；详细接入健康统一进入运行监控。

## 21. 应用管理

### 21.1 应用列表

路由：`/admin/apps`。

页面级操作位于页面标题右侧：

- 下载接口文件；
- 新增应用。

列表建议包含：

- 序号；
- 应用名称；
- 应用编码；
- 系统分类；
- 适用用户；
- 归属子系统；
- 启用状态；
- 运行状态；
- 操作。

操作：

- 编辑；
- 连接配置；
- 删除。

管理端新增、编辑应用时可维护归属子系统；新建应用必须选择 7 个整合后平台中的一个，编辑时可修正归属；现存 42 个纳管应用按原始清单对应关系回填。历史或异常数据若缺少归属，管理端列表和详情须明确显示“未归属”，不得以系统分类或名称相似度推断归属。归属变更只更新应用目录信息，不更改账号映射、入口授权、接入状态或审计历史。保存后需从数据库重新读取同一应用，核对稳定归属编码及展示名称。

删除规则：

- 所有应用均支持删除，不区分预置应用和后续新增应用；
- 删除前必须二次确认；
- 删除应用时同步清理该应用的连接配置、运行样本、账号映射、应用访问申请/授权、账号开通申请、待办、消息、访问记录及幂等接收记录等关联业务数据；
- 日志审计记录及接入状态变更历史保留，用于追溯曾执行过的删除操作与接入变化。

启用状态支持直接维护，操作列不重复提供等价的“启用/停用”操作。

应用名称作为详情入口。

列表排序规则：

- 应用名称、应用编码、综合运行状态、适用用户支持表头排序；
- 未主动排序时继续按既有显示顺序展示；
- 编辑已有应用时不再展示“显示排序”字段，避免在编辑业务信息时误改目录顺序；新增应用时仍可配置初始显示排序。

查询“适用用户”时按实际可适用范围匹配：

- 选择“公众用户”时，匹配仅公众（CITIZEN）以及公众及政务（BOTH）的应用；
- 选择“政务用户”时，匹配仅政务（GOV）以及公众及政务（BOTH）的应用；
- 选择“公众及政务”时，仅匹配 BOTH；
- 未选择适用用户时不限制该条件，展示管理端权限范围内的全部应用。

管理端应用列表必须基于纳管应用全量目录进行查询，不得按当前管理员自身用户类别过滤应用。

### 21.2 应用基本信息

详情字段顺序：

1. 应用名称、应用编码；
2. 系统分类、归属子系统、启用状态；
3. 适用用户、创建时间；
4. 运行状态；
5. 入口地址；
6. 说明。

统一将属于启停语义的“状态”命名为“启用状态”。

### 21.3 应用详情与查询边界

- PC 管理端“应用列表”保留关键词（应用名称/应用编码）、系统分类、综合运行状态、启用状态、适用用户查询。
- PC 公众门户“全部应用”展示关键词（应用名称/应用编码）、系统分类及归属子系统查询，不显示“综合运行状态”“适用用户”“启用状态”等管理专用条件；视图分组方式见第 14.1.1 节。
- 管理端点击应用名称打开“应用详情”，直接展示“基本信息”“连接信息”，不再设置单独的“应用信息”或“状态变更记录”Tab；接入历史统一从“运行监控”对应应用详情查看。
- PC“应用访问”结果弹窗按 PC 弹窗规范布局，不沿用移动端弹窗尺寸及交互。

### 21.4 应用访问模式配置

应用可配置：

- DIRECT（直接进入）；
- BIND（账号关联后进入）；
- REQUEST（申请通过后进入）。

三种模式的统一业务定义以 14.2“内部访问模式”为准，本节仅描述管理端配置关系。

REQUEST 可进一步配置申请通过后：

- DIRECT；
- BIND。

BIND 内部可配置账号处理模式：

- AUTO；
- SELF；
- REVIEW；
- ADMIN。

这些配置属于管理端，不直接暴露给普通用户。

### 21.5 连接配置

连接配置不建立独立一级菜单。

入口：应用列表 → 连接配置。

配置类型：

- SSO；
- TODO；
- MESSAGE。

配置内容按接入类型显示：

- 启用状态；
- 接入方式/协议；
- 服务地址；
- Client ID 等公开参数；
- 字段映射；
- 凭据引用；
- 备注。

敏感密钥不直接展示在页面或日志中，优先保存凭据引用。

连接信息展示列统一为：

- 接入类型；
- 接入方式；
- 配置状态；
- 启用状态。

第一次打开尚未初始化时，可初始化三类基础配置记录。

### 21.6 下载接口文件

“下载接口文件”为门户级公共接入规范，不属于单条应用行级操作。

应覆盖：

- SSO；
- TODO；
- MESSAGE；
- 标准字段；
- 请求/响应；
- 状态映射；
- 鉴权/幂等要求。

新增/编辑时门户角色使用平铺多选，不使用下拉多选。

密码和 password_hash 不得出现在列表、详情或普通 API 响应。

## 27. 组织管理

路由：`/admin/organizations`。

规则：

- 政务用户组织优先来源闽政务；

## 30. 通知公告管理

路由：

- `/admin/announcements`
- `/admin/announcements/:id`

### 30.1 生命周期

- DRAFT（草稿）；
- SCHEDULED（定时发布）；
- PUBLISHED（已发布）；
- WITHDRAWN（已撤回）；
- EXPIRED（已过期）。

### 30.2 功能

支持：

- 新增；
- 保存草稿；
- 立即发布；
- 定时发布；
- 预览；
- 已发布编辑；
- 撤回；
- 按规则删除；
- 正文插图；
- 附件；
- HTML/TXT 导入；
- 富文本正文一键清空；
- 正文加粗、斜体、下划线、文字大小、颜色、段落及列表等基础格式；选中文字后点击“斜体”应作用于选区并在编辑及展示时可见；
- 新增/编辑弹窗全屏编辑及退出全屏；

新增公告时必须直接选择发布方式：

- 立即发布：不显示“定时发布时间”字段，保存公告后立即进入 PUBLISHED；
- 定时发布：选择后才显示“定时发布时间”，且必须选择未来时间，保存后进入 SCHEDULED；日期选择器禁选过去日期，当日已过去的小时、分钟和秒不可选；提交前再次校验，服务端也必须验证未来时间；
- 用户也可以先“保存草稿”，草稿后续编辑时仍可选择立即发布或定时发布。

失效时间采用“失效日期”录入：

- 用户只选择日期，不要求输入具体时分秒；
- 留空表示永久有效；
- 选择日期后，系统统一按该日期当天 23:59:59 作为有效截止时间；
- 定时发布时间必须早于失效时间，避免公告尚未发布即已失效。

### 30.3 页面交互

- “新增公告”位于页面标题右侧；
- 新增公告选择“立即发布”时不显示“定时发布时间”；只有选择“定时发布”后才动态显示该字段；
- 新增公告、DRAFT草稿编辑、SCHEDULED定时公告编辑提供一致的业务字段与发布操作；
- 失效字段名称为“失效日期”，只选择日期；
- 公告标题作为详情入口；
- 管理端公告详情继续在右侧内容区打开，不使用详情弹窗；
- 公告编辑使用编辑弹窗，不通过路由切换到独立编辑页；
- 从列表点击“编辑”时直接打开编辑弹窗，关闭/取消后仍停留在公告列表，不应先跳转公告详情；
- 从公告详情点击“编辑”时打开编辑弹窗，关闭后仍停留在当前详情；
- 新增、DRAFT 草稿编辑、SCHEDULED 定时公告编辑三种场景提供相同的操作集合：取消、预览、保存草稿、立即发布/定时发布；
- DRAFT 草稿编辑时可保存草稿，也可直接立即发布或定时发布；选择定时发布后显示并必填定时发布时间；
- SCHEDULED 定时公告编辑时继续显示“发布方式”，默认选中“定时发布”；可调整正文、基础信息、定时发布时间和失效日期；
- SCHEDULED 定时公告点击“保存草稿”时，取消原定时计划并回到 DRAFT；点击“定时发布”则更新定时计划并保持 SCHEDULED；切换“立即发布”后点击立即发布则转为 PUBLISHED；
- PUBLISHED 已发布公告编辑时不再显示发布方式，点击“保存修改”后直接对当前已发布内容生效；
- WITHDRAWN 已撤回公告允许继续编辑和删除；编辑界面与新增、DRAFT、SCHEDULED保持相同字段排布和操作集合：取消、预览、保存草稿、立即发布/定时发布；
- WITHDRAWN编辑后点击“保存草稿”转为DRAFT；点击“立即发布”转为PUBLISHED；选择未来时间并点击“定时发布”转为SCHEDULED；重新发布后清除原撤回标记；
- EXPIRED 已过期公告不允许编辑，只允许删除；
- 左侧“通知公告管理”保持选中；
- 撤回操作需要确认；
- 删除操作需要二次确认，并明确删除后不可恢复；
- 新增和编辑公告均支持在普通弹窗尺寸与全屏编辑之间切换；关闭后再次打开默认恢复普通尺寸；
- 富文本编辑器支持“清空正文”，清空后正文内容同步为空；
- 公告附件最多 5 个，单个附件最大 20MB；正文插入图片仍按正文图片独立限制处理；
- 列表页与公告详情页必须遵循同一状态操作权限：WITHDRAWN 显示“编辑、删除”，其编辑弹窗可继续保存草稿或重新发布；EXPIRED 仅显示“删除”。

## 33. SSO / TODO / MESSAGE 接入

### 33.1 总体原则

每个应用可独立配置：

- SSO；
- TODO；
- MESSAGE。

配置入口唯一：应用列表 → 连接配置。

监控入口唯一：运行监控。

### 33.2 SSO

目标：

- 从门户进入目标子系统；
- 带入必要统一身份信息；
- 子系统自行进行业务授权。

具体协议可按系统能力采用：

- OIDC；
- SAML2；
- CAS/票据；
- Token；
- 自定义适配。

### 33.3 TODO

子系统通过 PUSH 将待办推送门户。

标准接入字段只要求：

- eventId；
- sourceTodoId；
- userId；
- status；
- title。

门户可根据应用配置补充来源应用名称、业务类型和业务跳转地址。

不要求同步：

- priority；
- dueAt / 截止时间；
- sourceRevision；
- terminalAt。

标准状态只接受 PENDING（待处理） / COMPLETED（已处理） / WITHDRAWN（已撤回）。

幂等使用 application + eventId 控制；同一 sourceTodoId 用于识别同一来源待办。终态后不得回退为待处理。门户不主动篡改子系统权威业务状态，也不根据时间自行判断逾期。

### 33.4 MESSAGE

子系统通过 PUSH 推送消息。

必须考虑：

- 应用鉴权；
- eventId；
- sourceMessageId；
- 用户；
- 标题；
- 正文；
- 来源；
- 幂等。

### 33.5 接口规范文件

门户应提供统一接入规范供子系统开发对接。

每个子系统的 Client ID、凭据引用、回调地址等个性参数由应用连接配置维护。

## 36. 核心业务流程

### 36.1 用户端登录

```text
选择公众用户或政务用户
→ 选择上层身份平台支持的认证方式
→ 完成身份校验并取得认证结果
→ 门户核验身份来源与用户状态，建立访问会话
→ 进入授权的用户端首页
```

### 36.2 管理端登录

```text
选择管理账号或已授权的上层身份入口
→ 完成适用的凭证与安全校验
→ 门户校验管理账号启用状态、管理角色及操作权限
→ 建立管理端会话
→ 进入管理首页
```

### 36.3 外部用户进入管理端

```text
闽政通/闽政务认证
→ Portal Session
→ 检查门户角色
→ 有管理角色：允许进入管理端
→ 无管理角色：仅普通用户端
```

### 36.4 应用访问

```text
用户点击应用
→ 校验应用启用状态
→ 校验适用用户类别
→ 校验门户入口资格
→ 必要时确认子系统账号关系
→ SSO/跳转
→ 子系统自行判定业务权限
```

### 36.5 REQUEST

```text
提交入口申请
→ PENDING
→ 管理员审核
→ APPROVED / REJECTED
→ APPROVED 后获得门户入口资格
→ 如仍需账号确认则继续
→ 进入应用
```

### 36.6 BIND 内部流程

```text
检查已有映射
→ 已 BOUND：进入
→ 未确认：后台发现候选关系
→ 必要的子系统/上层认证
→ 普通账号：BOUND
→ 高风险账号：REVIEWING
→ 冲突：CONFLICT
```

普通用户侧不展示这一技术过程，只展示结果与下一步。

### 36.7 公告

```text
DRAFT
→ 立即发布：PUBLISHED
→ 设置定时发布：仍保存为 DRAFT + publish_mode=SCHEDULED
→ 到达计划时间：PUBLISHED
PUBLISHED → WITHDRAWN
PUBLISHED + effective_end已到 → 页面派生显示 EXPIRED
```

PUBLISHED 允许按需求规则编辑；SCHEDULED、EXPIRED 为页面派生展示状态，不作为新增永久主状态。

### 36.8 待办/消息

```text
子系统 PUSH
→ 门户幂等接收
→ 按用户聚合
→ 用户查看
→ 业务处理跳回子系统
```

### 36.9 异常日志

```text
OPEN
→ 管理员查看与填写处理说明
→ RESOLVED
```

## 37. 通用交互要求

系统应满足以下通用交互要求：

- 页面能够完成对应业务功能和状态流转；
- 同一业务规则在首页、列表、详情等不同入口保持一致；
- 数据加载、无数据和加载失败应分别展示 Loading、Empty、Error 等明确状态，数据尚未完成加载时不得误显示为空；
- 面向业务用户的界面使用业务语言，不直接暴露内部状态机代码、接口实现术语或技术异常细节；
- 关键提交、撤回、删除、解绑、审核等操作应根据风险提供必要的二次确认；
- 操作成功后提供明确结果反馈，操作失败时提供可理解的错误原因和下一步建议；
- 列表无数据时使用统一空状态表达，并提供明确的无数据说明；
- 列表或表格中的文本因列宽限制被省略时，鼠标悬浮应显示该字段完整内容；未发生截断时不重复显示浮层，操作按钮、开关、状态标签等非纯文本内容不强制使用该提示；
- 详情、编辑、弹窗及返回行为应保持业务上下文连续，避免因页面跳转造成状态或导航上下文丢失；
- 具体视觉设计、组件选型、字号、颜色、间距、图标及视觉验收标准由配套设计规范定义，不在本文中重复约束。

## 39. 数据隔离与安全

### 39.1 用户数据隔离

用户端：

- 待办只看本人；
- 消息只看本人；
- 公告按发布范围；
- 应用按用户类别、适用范围、入口资格和映射结果；
- 我的申请只看本人。

管理端根据角色权限访问管理数据。

### 39.2 凭据保护

不得记录：

- 外部身份密码；
- 子系统明文密码；
- OTP；
- Token；
- password_hash。

敏感连接凭据使用环境变量/凭据引用等方式管理。

### 39.3 后端鉴权

高风险写操作必须服务端二次鉴权，不能只依赖前端隐藏按钮。

### 39.4 审计

关键动作需记录：

- 操作人；
- 对象；
- 动作；
- 结果；
- 时间；
- 请求ID；
- 必要上下文。

## 40. 非功能性要求

### 40.1 可用性

- 常用操作路径清晰；
- 用户侧尽量使用业务语言；
- 不向普通用户暴露底层状态机和接口实现术语；
- 同一业务在不同入口遵循相同的权限、状态和数据规则。

### 40.2 业务一致性

- 业务术语统一；
- 状态枚举与状态含义统一；
- 权限判断和数据范围规则统一；
- 同一业务动作的前置校验和结果语义统一。

### 40.3 可扩展性

- RBAC 支持未来自定义角色；
- 数据范围支持未来扩展；
- 应用支持多种 SSO；
- 接入配置支持多子系统差异；
- 用户索引允许未来扩展身份来源。

### 40.4 可追溯性

- 重要状态流转有日志；
- 请求带 requestId；
- 应用接入支持幂等；
- 映射冲突处理保留证据。

8. 42项纳管系统的最终名称、编码、入口地址及逐系统接入资料；
9. 各应用适用用户范围；
10. 各应用 DIRECT/BIND/REQUEST 模式；
11. 各 BIND 应用的具体账号确认方式；
12. 各子系统 SSO 方式；
13. 各子系统是否提供账号查询/校验/认证接口；
14. 哪些账号属于高权限账号；
15. 是否允许用户自行解绑/重绑；
16. 应用入口授权是否设置有效期；
17. 闽政务组织同步方式和稳定组织ID；
18. 公告定时发布调度方案；
19. 公告附件/正文图片正式存储方案；
20. 运行监控真实探测频率与异常阈值；
21. 42项纳管系统是否按7个整合后平台进行页面分组或“平台+下属系统”二级目录展示；纳管数量本身已确认为42项；
22. 原始需求中的完整用户主数据维护、用户新增/修改/作废是否仍由门户建设，还是全部由闽政通/闽政务等上层身份平台负责；
23. 法人/企业用户是否属于本门户用户范围；
24. “每个用户都隶属组织”是否仍为硬性要求，公众用户是否允许无组织；
25. 应用访问控制最终采用原始需求的“角色→应用授权”，还是当前 DIRECT/BIND/REQUEST + 用户申请/入口资格模式，或两者并存；
26. 门户是否需要统一创建/分配子系统账号，还是只做子系统账号映射与申请状态承接；
27. 是否需要用户组管理、自定义角色删除，以及独立“权限管理”菜单；
28. 待办未及时处理时的定期催办是否由门户负责，若负责需确认周期、停止条件、提醒渠道和截止时间来源；
29. 公告“固定格式”是否要求可维护的公告模板/套红模板，以及是否需要按组织、角色、指定人员精细发布；
30. 短信管理是否属于本项目；如属于，需确认渠道、模板、定时发送、发送记录、失败重发、费用数据来源及运营责任；
31. 原始需求中的应用版本/业务状态/性能阈值和角色个性化界面是否仍需由门户配置；
32. 是否必须提供可配置日志策略、登出日志和权限检测日志；
33. 统一数据采集汇聚、三医数据治理和专项库建设是否属于本门户范围，还是由独立数据平台承担；
34. 统一预约/检验互认/健康档案等通用业务服务接口改造是否属于本项目，还是门户仅负责SSO/TODO/MESSAGE；
35. 分布式调用链、APM、日志分析等微服务治理能力是否由省一体化支撑平台提供，门户只保留接入健康摘要；
36. 原始清单中的网络区域是否影响门户可见性、跳转、VPN/专线或接入策略；
37. 是否要求批量同步各子系统用户/角色数据，还是仅维护应用目录和必要账号映射。

上述原始需求差异的完整说明见《细化需求/原始需求与当前实现差异及客户确认清单.md》。待确认项未明确前，不应将假设写成正式业务事实。

## 44. 建设与交付边界

- 本系统面向 42 项纳管业务子系统，支持统一应用目录、访问申请、账号关联、待办消息接入、公告发布、身份映射、运行监控及审计管理。
- 闽政通、闽政务身份认证及目标子系统的对接按权威身份平台、目标系统提供的接口契约和双方确定的联调计划实施，门户不代替外部系统承担账号或业务权限管理职责。
- SSO、TODO、MESSAGE 等接口应明确必填字段、状态、鉴权、幂等、错误码、时间格式和用户定位规则；“下载接口文件”应输出结构有效、字段一致的 OpenAPI 文件。
- 连接配置仅保存允许落库的参数及凭据安全引用；明文密码、验证码、密钥与敏感令牌不得进入业务明细或对外文档。
- 业务数据存储结构、数据迁移、外部接口联调、上线环境和安全验收按项目实施与交付计划分别核验。
- 每一项建设功能的完成情况、对接范围和遗留问题应以相应的测试、联调和正式验收记录为依据，不得以需求清单替代实施完成确认。

## 45. 验收原则

### 45.0 业务功能验收范围

功能验收覆盖授权范围内的页面显示、查询与分页、详情与操作、状态流转、业务闭环、权限隔离、业务数据持久化、日志审计与接口契约可用性。外部身份平台联调、目标业务子系统接口验证、生产环境部署等应按约定的独立条件组织专项验收，未经验证不得视为通过。

### 45.1 身份与权限

- 闽政通/闽政务两类用户端身份来源识别正确；
- LOCAL 仅作为门户本地管理认证方式，不作为第三类用户端身份；
- 用户类别、认证类型与门户角色不混用；
- 无管理角色用户不能进入管理端；
- LOCAL 可独立登录；
- 默认角色仅超级管理员和门户管理员；
- 子系统业务权限不进入门户角色管理。

### 45.2 用户端

- 数据按当前用户隔离；
- 我的应用只显示已可使用应用；
- 其它应用显示结果和下一步，不暴露技术过程；
- 应用申请闭环；
- 账号异常/未开户/停用有明确结果；
- 待办、消息、公告正常展示；
- Loading 不闪 Empty。

### 45.3 管理端

- 应用、用户、角色、组织、字典、映射、配置可按权限管理；
- 应用连接配置入口唯一；
- 启用状态维护正确生效；
- 身份映射详情分区和分页正确；
- 日志字段按类型展示；
- 异常日志可闭环；
- 运行监控只承担接入健康查看。

### 45.4 交互验收

- 页面功能入口可正常使用；
- Loading / Empty / Error 状态语义正确；
- 详情、编辑、提交、撤回、删除等操作遵循已确认业务规则；
- 页面不向业务用户暴露内部状态机代码、研发实现术语或不必要的技术状态；
- 视觉表现按照配套设计规范进行验收，本文重点验收业务功能、状态、权限、流程及交互结果。

### 45.5 安全

- 明文密码不落库；
- password_hash 不返回前端；
- OTP/Token 不写日志；
- 高风险操作服务端鉴权；
- 映射冲突不得自动覆盖；
- 关键操作可追溯。

## 48. 移动端页面与交互需求

本章属于《卫健统一门户系统需求规格说明书》的正式组成部分，统一定义移动端页面、路由、业务字段、状态操作及交互规则，不另行维护移动端需求文档。移动端与 PC 用户端共用身份会话、应用访问授权、申请、待办、消息、公告及个人数据等业务规则；移动端 UI 采用独立的导航、布局和弹窗。移动端的功能完成情况与接口联调、终端验收分别记录，不以需求章节代替验收结论。

### 48.1 适用用户与功能边界

- 使用对象：公众用户（`CITIZEN`）、政务用户（`GOV`），可见应用、待办、消息、申请及公告均遵循用户身份与适用范围控制。
- 统一业务名称：**首页、待办事项、消息中心、全部应用、我的**；“通知公告”“我的申请”为从业务入口到达的页面；移动端底部使用“我的”，与 PC 用户端“个人中心”指向同类个人服务。
- 业务功能沿用本文件 PC 用户端相应章节要求；移动端不承接 PC 管理端的应用列表配置、公告发布、角色权限、审计日志和运行监控等后台管理职能。
- 登录与会话复用本文件第 11、36、39 章的身份和安全规则，移动端不另建独立身份体系；进入子系统须执行适用的访问授权与 SSO 规则。

### 48.2 页面路由及入口

| 路由 | 页面名称 | 主要内容与入口 | 详情方式 |
|---|---|---|---|
| `/m` | 移动端入口 | 跳转 `/m/home` | - |
| `/m/home` | 首页 | 我的应用、我的申请快捷入口、通知公告、待办事项 | 通过入口进入对应业务 |
| `/m/todos` | 待办事项 | 待办检索、状态筛选、待办列表 | 列表内移动端详情弹窗 |
| `/m/messages` | 消息中心 | 消息列表、未读提示、阅读状态与类型等筛选 | `messageId` 查询参数进入消息详情 |
| `/m/apps` | 全部应用 | 应用分类侧栏、关键词搜索、应用访问和账号处理、我的申请入口 | 移动端业务弹窗 |
| `/m/profile` | 我的 | 个人信息与个人服务入口 | 页面内容 |
| `/m/announcements` | 通知公告 | 公告列表与阅读状态提示 | 点击进入独立详情路由 |
| `/m/announcements/:id` | 公告详情 | 标题、发布信息、正文、附件 | 独立详情路由 |
| `/m/applications` | 我的申请 | 应用访问申请、账号开通申请及其进度 | 列表及操作 |
| `/m/applications/:id` | 申请详情 | 申请信息、审核或处理信息、状态及允许的操作 | 独立详情路由 |

以上 URL 为移动端页面路由；不存在单独的“待办详情”路由，待办通过页面内弹窗展示；消息详情由 `messageId` 维护页面上下文。

### 48.3 主导航、面包屑与返回上下文

1. 底部主导航固定为“首页、待办事项、消息中心、全部应用、我的”，支持当前栏目选中状态；待办及消息存在未处理、未读数据时可显示提示标识。
2. “我的申请”列表和申请详情使用顶部返回，不展示底部主导航；消息进入详情状态时隐藏底部主导航；公告详情按公告模块的顶部返回规则执行。
3. 从首页进入“我的申请”时携带 `from=home`；从“全部应用”进入时携带 `from=apps`。申请详情应继续保留 `from` 和当前申请类别 `tab`，返回时先回原申请列表及类别，再由列表返回首页或全部应用；无来源参数时返回“我的”。
4. 公告详情返回公告列表，公告列表返回首页。消息详情退出后返回消息列表，不应意外切换到其他底部栏目。
5. 进入详情后，遮罩、顶部返回、Tab 选中、滚动位置及列表查询上下文不得相互干扰；由不同业务入口进入时，优先回到用户实际来源页面。

### 48.4 首页

- “我的应用”展示当前用户可访问的应用，提供进入应用和前往“全部应用”的入口；应用访问状态与全部应用保持一致。
- “我的申请”作为快捷入口，进入申请列表时标明来源为首页；从申请详情返回后应回到首页，不得错误跳转到“我的”。
- 展示最新通知公告，可进入公告详情和通知公告列表；展示待办摘要及待处理数量，可进入待办事项。
- 首页模块在无数据、加载中或网络异常时展示相应状态，不显示过期的上一用户数据。

### 48.5 待办事项

- 查询与列表：按标题关键词、待办状态等条件筛选；列表展示标题、来源应用、业务类型或摘要、接收时间和状态等有效字段。
- 点击待办卡片弹出移动端居中详情，**标题直接使用该待办标题**；详情展示标题、来源应用、业务类型、接收时间、状态和待办说明，字段口径与 PC 用户端一致。
- 详情右上角提供关闭图标，不额外增加“待办详情”固定标题或重复的“关闭”底部按钮；仅 `PENDING`（待处理）显示“去处理”。
- “去处理”负责跳转来源业务，不直接将门户待办写成“已处理”；最终业务状态由来源子系统更新，待办终态不逆转。

### 48.6 消息中心

- 提供消息列表、未读提示、阅读状态、消息类型以及时间范围等可用筛选；列表展示标题、来源信息、接收时间、已读/未读提示。
- 点击消息进入同一路由携带 `messageId` 的详情状态，显示消息标题、正文、来源信息及相关业务入口；阅读状态遵循门户消息规则。
- 详情支持返回消息中心，并按实际消息状态提供前后消息切换或可用操作；消息详情不叠加底部主导航。
- 用户仅能查看本人有权限接收的消息；删除、标记已读等操作遵循本文件消息中心的业务与权限规则。

### 48.7 全部应用与账号确认

- “全部应用”采用移动端现有分类侧栏及关键词搜索，关键词支持应用名称、编码等；保留左侧应用分类栏和现有页面样式，头部不增加“归属子系统”查询或按子系统视图切换按钮。移动端与 PC 端共用应用数据及当前用户权限范围，但本轮新增归属查询和分组视图只用于 PC 门户。
- 应用卡片显示应用名称、分类及有效访问状态；按 `DIRECT`、`BIND`、`REQUEST` 等接入模式提供进入、账号确认或申请使用操作，具体执行须经过服务端权限和状态校验。
- 申请使用弹窗要求填写申请原因，提交后可在“我的申请”查看审核进度；缺少必填内容不允许提交。
- 应用访问结果、账号确认和绑定引导使用**移动端独立弹窗**，与 PC `AccountBindingWizard` 的布局、尺寸和操作按钮区分；绑定完成后按有效结果提供后续进入方式，异常状态显示清晰处理提示。
- 应用访问或账号操作失败时应允许关闭弹窗并保留原列表及分类，不应未经授权直接进入子系统。

### 48.8 我的申请与申请详情

- 申请列表支持“应用访问申请”“账号开通申请”类别切换，展示申请编号、目标应用、申请类型、当前状态、提交时间及相关处理信息。
- 点击申请进入 `/m/applications/:id`，详情分组呈现申请基本信息、业务说明、审核或处理结果及时间；保留进入时的申请类别与页面来源。
- 仅在业务状态允许时显示相应操作。例如待处理的应用访问申请可发起撤回；满足重新申请条件的记录可再次进入应用申请入口。
- 申请状态由对应业务流程或来源系统确认，页面不可绕过权限、申请有效性或审核规则直接改变授权结果。

### 48.9 通知公告及“我的”

- 通知公告列表展示标题、类型、发布时间及未读提示；点击进入详情，详情显示标题、发布日期、正文以及附件列表，允许按权限下载有效附件。
- 公告可见范围、发布与失效状态、用户已读记录等规则与 PC 用户端一致；不可访问的公告应显示明确提示，不泄露正文。
- “我的”展示当前登录用户可见的个人信息与服务入口；不能由该入口修改上层身份平台负责维护的权威身份字段。

### 48.10 移动端弹窗与终端差异规范

- 待办详情、应用访问结果、账号确认、申请操作确认等弹窗采用适合移动设备的宽度、内边距、触控区域、关闭方式和可滚动内容。
- 弹窗打开时遮罩覆盖底部导航层，导航不得浮于遮罩之上；对话框正文与边框留白统一，操作按钮及关闭图标不重复、不错位。
- 同一业务在 PC 与移动端的字段定义、状态、权限和服务端校验保持一致，允许根据终端使用不同列表、抽屉或详情呈现；PC 管理端组件不直接作为移动端界面规范。
- 页面标题、导航和按钮名称统一使用“全部应用”“待办事项”“消息中心”；PC 管理端“应用列表”“应用管理”“通知公告管理”仍表示独立管理职能，不能混用为普通用户页面标题。
