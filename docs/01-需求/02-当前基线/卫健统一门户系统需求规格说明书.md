## 2. 建设背景与目标

卫健统一门户用于在闽政通、闽政务等上层权威身份体系与多个卫健业务子系统之间建立统一访问入口。

建设目标：

- 提供统一登录入口；
- 承接闽政通、闽政务两类外部访问身份，并建立独立的门户管理用户授权体系；
- 建立统一用户索引，但不重复建设完整公众/政务身份库；
- 聚合用户可访问的业务应用；
- 支持应用入口申请、账号确认及访问前校验；
- 聚合待办、消息和门户公告；
- 为管理员提供应用、用户、角色、组织、字典、映射、配置、日志及接入健康管理；
- 保持门户入口权限与子系统业务权限严格分离；
- 为各业务子系统提供统一 SSO / TODO / MESSAGE 接入规范；
- 形成业务闭环完整、可持续接入业务子系统的统一门户能力。

## 3. 系统定位

### 3.1 总体关系

```text
闽政通 ──→ 公众用户 CITIZEN ┐
闽政务 ──→ 政务用户 GOV    ├─→ 门户访问主体 ─→ 用户端/业务子系统
                                 │
门户管理用户（独立授权主体） ───┴─→ 管理端
  ├─ 可绑定闽政通/闽政务身份
  └─ 可使用门户本地管理账号
```

卫健统一门户位于身份来源与业务子系统之间，承担“统一身份承接 + 门户入口授权 + 应用聚合 + 公共事务聚合 + 管理支撑”。

### 3.2 门户不是

门户不是：

- 闽政通/闽政务的替代身份平台；
- 子系统统一用户主库；
- 子系统统一角色中心；
- 子系统统一菜单权限中心；
- 子系统统一数据权限中心；
- 子系统业务审批平台；
- 复杂 APM、服务器监控或链路追踪平台。

### 3.3 总体原则

> 统一身份承接 + 门户入口授权 + 子系统分布式业务授权。

门户决定“用户能否从门户看到、申请、进入某个应用”，子系统决定“用户进入后拥有什么业务角色、菜单、数据和操作权限”。

## 4. 建设范围与责任边界

### 4.1 上层身份平台负责

闽政通负责公众用户权威身份，闽政务负责政务用户权威身份。

上层平台负责：

- 正式身份注册/开通；
- 实名认证；
- 外部账号安全；
- 外部身份核心状态；
- 扫码、手机号验证码等上层认证能力；
- 手机号登录所需的安全识别、风险控制、动态验证码发送、验证码有效期、重发间隔、频率限制和验证码校验；
- 短信验证码发送能力及短信通道由闽政通、闽政务或其统一短信服务提供；
- 如具备条件，可提供人脸等强身份核验能力。

门户不自行保存公众/政务用户人脸模板。

### 4.2 统一门户负责

门户负责：

- 统一登录入口；
- 闽政通/闽政务认证结果承接；
- 独立门户管理用户及门户本地管理账号认证；
- Portal Session；
- 统一用户索引；
- 用户类别识别；
- 门户访问主体状态与门户管理用户启用状态；
- 门户角色和 MENU / PAGE / ACTION 权限；
- 本地管理账号生命周期；
- 应用目录；
- 应用适用用户规则；
- DIRECT / BIND / REQUEST 入口模式；
- 应用访问申请；
- 应用入口授权；
- 子系统账号映射；
- 映射审核、异常和冲突处理；
- 待办、消息聚合；
- 门户公告；
- 组织索引；
- 字典与配置；
- SSO / TODO / MESSAGE 接入配置；
- 接入健康查看；
- 登录、访问、操作、接口、异常日志。

### 4.3 业务子系统负责

子系统负责：

- 子系统账号本体；
- 子系统开户注册；
- 子系统账号启停；
- 子系统业务角色；
- 子系统菜单权限；
- 子系统数据权限；
- 子系统业务审批；
- 业务状态；
- 高权限账号管理；
- 子系统自身认证/授权页；
- 子系统已有账号真实性；
- 子系统原登记手机号 OTP 或账号校验接口（如提供）。

### 4.4 首期不纳入范围

首期不建设：

- 公众用户完整生命周期管理；
- 政务人员完整生命周期管理；
- 外部用户密码管理；
- 面向公众开放门户本地管理账号自助注册；
- 子系统业务角色统一维护；
- 子系统菜单/数据权限集中维护；
- 门户替子系统直接创建业务账号；
- 复杂组织数据权限；
- 复杂应用级数据范围；
- 收藏应用；
- 复杂运维 APM；
- 短信费用统计。

## 5. 核心术语

| 术语 | 含义 |
|---|---|
| 身份来源 | MINZHENGTONG / MINZHENGWU（用户端外部身份） |
| 用户类别 | CITIZEN / GOV（用户端访问类别） |
| 门户角色 | SUPER_ADMIN / PORTAL_ADMIN / 后续自定义门户角色 |
| Portal Session | 统一门户登录后的会话 |
| 应用入口资格 | 用户是否可从统一门户进入某应用 |
| 子系统业务权限 | 用户进入子系统后由子系统判定的业务权限 |
| DIRECT | 满足适用范围后无需门户账号映射即可进入 |
| BIND | 进入前需要确认统一用户与子系统账号关系 |
| REQUEST | 进入前需要先取得门户应用入口资格 |
| BOUND | 子系统账号映射已有效确认 |
| TODO | 子系统推送至门户的待办 |
| MESSAGE | 子系统或门户产生的消息 |
| SSO | 门户到子系统的单点/统一跳转能力 |

## 6. 外部身份、门户访问主体与门户管理用户

三者必须严格分离。

### 6.1 外部身份与用户类别

| 身份来源 | 用户类别 | 权威主体 | 首期主要入口 |
|---|---|---|---|
| MINZHENGTONG / 闽政通 | CITIZEN / 公众用户 | 闽政通 | 用户端 |
| MINZHENGWU / 闽政务 | GOV / 政务用户 | 闽政务 | 用户端 |

规则：

- 身份来源不是门户角色；
- 用户类别不是门户角色；
- 门户不建设公众/政务用户完整身份生命周期；
- 权威姓名、账号、手机号等外部主数据不可由门户任意修改。

### 6.2 门户访问主体

门户为用户端保存最小必要统一索引，用于 Portal Session、待办、消息、应用中心、账号映射和审计。

现有 `unified_user` 在目标设计中继续承担这一职责，但只表示 CITIZEN/GOV 门户访问主体，不再承载本地管理账号。

### 6.3 门户管理用户

管理端使用独立 `portal_admin_user` 授权主体。

门户管理用户可以：

- 绑定一个闽政通/闽政务门户访问主体；
- 或使用门户本地管理账号认证。

是否可以进入管理端，由 `portal_admin_user.enabled + portal_role + portal_permission` 决定，不由用户类别自动决定。

### 6.4 跨身份源关系

CITIZEN 与 GOV 不默认自动合并。若未来需要跨源关联，应优先使用稳定权威跨源ID；没有稳定ID时采用候选匹配 + 上层重新认证/更强身份核验，不得仅凭姓名+手机号自动合并。

## 7. 门户管理用户与本地管理账号

### 7.1 门户管理用户

管理端“用户管理”管理的是门户管理用户，不是所有访问过门户的公众/政务用户。

管理用户至少包含：

- 管理用户ID；
- 展示账号/姓名；
- 认证类型：EXTERNAL / LOCAL；
- 外部访问主体绑定（EXTERNAL时）；
- 启用状态；
- 门户角色；
- 最近登录时间。

停用门户管理用户只取消管理端访问资格，不影响其上层闽政通/闽政务账号，也不影响其仍满足条件时使用用户端。

### 7.2 本地管理账号

本地账号用于初始化、运维或没有上层身份的管理人员。

本地管理账号直接属于 portal_admin_user，不再建立 LOCAL 普通访问用户。

本地凭证单独维护：

- username；
- password_hash；
- password_algorithm；
- must_change_password；
- failed_login_count；
- locked_until；
- password_updated_at；
- last_login_at。

规则：

- 不开放公众自助注册；
- 密码必须安全哈希；
- 明文密码、OTP、Token 不进入普通日志；
- 本地账号不自动等于管理员，仍必须分配有效门户角色；
- 最后一个有效超级管理员必须受后端事务保护。

### 7.3 外部身份管理员

闽政通/闽政务用户可以被授予管理资格。授权时仅建立 portal_admin_user 与访问主体的绑定，不复制成“本地用户”，也不改变其原用户类别。

## 8. 门户角色与权限模型

### 8.1 默认角色

首期只预置：

| 角色 | 编码 | 定位 |
|---|---|---|
| 门户超级管理员 | SUPER_ADMIN | 最高门户管理权限 |
| 门户管理员 | PORTAL_ADMIN | 日常门户维护 |

预计实际维护人员较少，因此首期不预置应用管理员、公告管理员、审计管理员、集成管理员等大量细分角色。

### 8.2 权限模型

门户 RBAC 支持：

```text
菜单 MENU
  └─ 页面 PAGE
       └─ 操作 ACTION
```

首期两个默认管理角色数据范围按 ALL_PORTAL 处理。

SELF / ORG / ORG_AND_CHILDREN / ASSIGNED_APPS 等数据范围作为后续扩展，不作为首期复杂配置项。

### 8.3 超级管理员

默认拥有：

- 全部管理端菜单；
- 全部页面；
- 全部操作；
- 用户及本地账号管理；
- 角色权限管理；
- 组织、字典、配置；
- 应用、公告、映射、监控、日志；
- 管理员授权；
- 本地用户密码重置；
- 关键配置维护。

系统必须保护最后一个有效超级管理员账号和超级管理权限。

### 8.4 门户管理员

默认承担日常维护：

- 管理首页；
- 通知公告；
- 应用目录；
- 应用访问申请；
- 子系统账号开通申请状态（如启用）；
- 运行监控；
- 身份与子系统映射；
- 用户查询及必要门户侧维护；
- 组织；
- 字典；
- 日志审计。

高风险操作可只允许超级管理员：

- 创建/删除本地管理账号；
- 重置其他管理员密码；
- 角色权限配置；
- 超级管理员授权；
- 删除关键配置。

### 8.5 子系统权限隔离

门户角色不得：

- 创建子系统业务角色；
- 修改子系统业务角色；
- 分配子系统菜单；
- 分配子系统数据权限；
- 代替子系统完成业务审批。

## 9. 用户端与管理端关系

“用户端”和“平台管理端”是两个使用入口，不是两个用户类别。

### 9.1 用户端

首期主要面向：

- CITIZEN；
- GOV。

### 9.2 管理端

进入管理端必须拥有有效门户管理角色。

管理端访问主体统一为门户管理用户。门户管理用户可绑定闽政通/闽政务访问主体，也可使用门户本地管理账号；是否能进入管理端由有效 portal_admin_user 与门户角色共同决定。

### 9.3 端切换

同一 Portal Session 下，若当前用户同时具备用户端和管理端访问资格，可提供“用户端门户 / 平台管理端”切换，不要求重复登录。

## 10. 信息架构与菜单

### 10.1 用户端门户

当前用户端左侧导航采用单层菜单，不再显示“个人事务”“应用中心”等一级分组标题。

```text
用户端门户
├─ 首页
├─ 待办任务
├─ 消息中心
├─ 通知公告
├─ 应用中心
├─ 我的申请
└─ 个人中心
```

菜单与页面关系：

- 首页 → `/portal/home`；
- 待办任务 → `/portal/todos`；
- 消息中心 → `/portal/messages`；
- 通知公告 → `/portal/announcements`；
- 应用中心 → `/portal/apps/all`；
- 我的申请 → `/portal/applications`；
- 个人中心 → `/portal/profile`。

补充规则：

- “应用中心”在左侧菜单中只显示一个入口；
- “我的应用 / 其它应用”属于应用中心页面内部的数据分组，不作为左侧子菜单；
- `/portal/apps/mine` 仅保留兼容隐藏路由，不作为当前用户端菜单入口；
- 公告详情、消息详情等详情页面不单独占用左侧菜单项，进入详情后保持对应业务菜单上下文；
- 用户端左侧菜单显示顺序以本节为当前需求基线。

├─ 用户管理
├─ 角色管理
├─ 组织管理
├─ 字典管理
├─ 身份与子系统映射
└─ 配置管理

日志审计
├─ 登录/认证日志

├─ 门户操作日志
├─ 接口调用日志

## 11. 统一登录

### 11.1 路由
统一登录路由：`/login`。用户端和管理端共用同一个登录页。

### 11.2 当前原型入口
- 公众用户：模拟闽政通身份，点击“进入系统”直接建立对应 Mock Session 并进入用户端；
- 政务用户：模拟闽政务身份，点击“进入系统”直接建立对应 Mock Session 并进入用户端；
- 管理账号：模拟门户本地管理员，固定演示账号为 `admin`，点击“进入管理端”直接进入管理端。

### 11.3 原型交互规则
当前项目为高保真演示原型，登录页不要求用户完成真实身份认证操作：
- 不展示或操作二维码；
- 不要求输入手机号；
- 不要求滑块或其它安全验证；
- 不要求输入短信验证码；
- 管理账号不要求输入密码或图形验证码；
- 身份 Tab 只用于选择本次演示身份；
- 点击进入按钮后，由 Mock Service 建立对应的 Portal Session。

### 11.4 身份语义
- 公众用户：`MINZHENGTONG / CITIZEN`；
- 政务用户：`MINZHENGWU / GOV`；
- 管理账号：`PORTAL_LOCAL / portal_admin_user`；
- 管理账号 `admin` 默认使用 `SUPER_ADMIN` 演示权限。

### 11.5 Portal Session
- 公众/政务用户 → `/portal/home`；
- 管理账号 → `/admin/home`。

真实闽政通、闽政务认证方式及生产级本地账号认证不属于当前原型验收范围。

## 12. 认证结果页

路由：`/auth/result`。

状态：

- SUCCESS（成功）；
- FAILURE（失败）；
- DISABLED（账号停用）；
- LOCKED（账号锁定）；
- NO_PERMISSION（无权限）；
- UPSTREAM_ERROR（上层认证异常）；
- SESSION_ERROR（会话建立失败）。

页面显示：

- 认证来源；
- 结果状态；
- 请求ID（存在时）；
- 状态说明；
- 下一步操作。

操作：

- SUCCESS → 进入目标端；
- NO_PERMISSION → 有普通用户 Session 时返回用户端；
- FAILURE / UPSTREAM_ERROR / SESSION_ERROR → 重新登录；

## 14. 应用中心

路由：`/portal/apps/all`。

### 14.1 分组

应用中心分为：

- 我的应用；
- 其它应用。

“我的应用”只展示当前已经满足访问条件的应用。

“其它应用”只展示当前用户可见但仍需申请、账号确认、等待处理或异常处理的应用。

不得向普通用户展示无适用范围的全部后台应用目录。

### 14.2 内部访问模式

门户内部支持三种应用入口模式：

| 模式代码 | 中文名称 | 核心含义 | 用户侧主要表现 |
|---|---|---|---|
| DIRECT | 直接进入 | 用户满足应用启用、适用用户范围和入口可用等基础条件后，无需额外提交门户访问申请，也无需先建立子系统账号映射，即可直接进入后续 SSO / 应用跳转流程。 | 进入应用 |
| BIND | 账号关联后进入 | 用户进入应用前，需要先确认当前门户统一身份与目标子系统账号之间的对应关系；关联完成且账号可用后，才能继续进入目标应用。 | 申请使用 / 查看进度 / 进入应用 |
| REQUEST | 申请通过后进入 | 用户进入应用前，需要先提交门户应用访问申请；审核通过后取得门户入口资格，再根据该应用配置决定直接进入，或继续完成子系统账号关联。 | 申请使用 / 查看申请 / 完成账号确认 / 进入应用 |

三种模式分别解决不同问题：

- DIRECT：表示用户不需要经过额外申请或账号关联即可进入应用；
- BIND：解决“当前门户身份对应哪个子系统账号”的问题；
- REQUEST：解决“当前用户是否具备从门户进入该应用的入口资格”的问题。

补充规则：

- REQUEST 审核通过只代表取得门户入口资格，不代表获得目标子系统内部业务角色、菜单或数据权限；
- REQUEST 可以配置审核通过后进入 DIRECT 或继续进入 BIND；
- BIND 只管理门户统一身份与子系统账号的映射关系，不替代子系统自身的账号、角色和权限管理；
- 以上代码属于门户内部访问控制模型，普通用户页面不直接展示 DIRECT / BIND / REQUEST；“其它应用”卡片的初始主操作统一采用“申请使用”，进入后续流程后再根据实际结果显示账号确认、查看进度、查看原因等业务化操作。

### 14.3 DIRECT

满足：

- 应用已启用；
- 用户类别适用；
- 应用入口允许；

即可直接进入后续 SSO/跳转。

### 14.4 REQUEST

REQUEST 用于控制门户入口资格。

状态：

- PENDING（待审核）；
- APPROVED（已通过）；
- REJECTED（已驳回）；
- WITHDRAWN（已撤回）；
- EXPIRED（已失效）。

申请通过只代表“获得门户入口资格”，不代表获得子系统业务权限。

### 14.5 BIND

BIND 内部支持：

- AUTO；
- SELF；
- REVIEW；
- ADMIN。

用户侧不显示这些代码。

### 14.6 用户侧结果导向交互

用户侧以“当前结果 + 下一步操作”为核心。

可见操作收敛为：

- 进入应用；
- 申请使用；
- 完成账号确认；
- 查看申请；
- 查看进度；
- 继续处理；
- 查看原因；
- 重新处理。

可见状态使用业务化文案：

- 待申请；
- 申请处理中；
- 申请未通过；
- 需确认账号；
- 待继续处理；
- 处理中；
- 处理失败；
- 账号异常；
- 账号不可用。

不得直接把 BIND、VERIFYING、REVIEWING、CONFLICT 等代码暴露给普通用户。

“其它应用”卡片展示规则：

- 第一行显示应用名称；
- 第二行显示应用类型；
- 第三行单独显示当前状态和下一步操作，避免与应用类型挤在同一行；
- 对尚未具备使用条件、需要进入账号处理流程的应用，卡片初始主操作统一显示“申请使用”，不直接显示“完成账号确认”；
- 点击“申请使用”后，再根据实际情况进入门户访问申请、账号确认、开户注册或其它后续处理流程；
- “账号异常 / 查看原因”“处理失败 / 重新处理”“申请处理中 / 查看申请”等状态与操作必须在独立结果行中展示。

### 14.7 已有历史账号

当需要历史账号、密码、验证码或子系统自身认证时：

1. 门户先判断是否已有有效映射；
2. 如可通过可信唯一标识唯一确认，可在后台直接完成；
3. 如需用户认证，门户显示“需要完成账号确认”；
4. 用户点击“前往子系统确认”；
5. 历史账号、密码、验证码等在目标子系统输入；
6. 门户不采集这些凭据；
7. 用户完成后返回门户；
8. 门户通过回调/标准接口/重新检测更新结果。

### 14.8 未检测到子系统账号

显示：

> 需要开通账号。

默认操作：

- 前往子系统开通；
- 完成后重新检测。

规则：

- 门户不直接创建子系统账号；
- 开户规则由子系统决定；
- 只有子系统提供标准开户申请接口时，门户才可承接申请提交与状态回显。

### 14.9 高权限账号

高权限账号可在完成必要确认后进入 REVIEWING，待门户管理员审核。

用户侧只显示“处理中/账号确认已提交”。

### 14.10 冲突和失败

至少区分：

- ACCOUNT_NOT_FOUND（未找到账号）；
- INVALID_CREDENTIALS（账号凭证错误）；
- OTP_INVALID（验证码错误）；
- OTP_EXPIRED（验证码已过期）；
- ACCOUNT_DISABLED（账号已停用）；
- ACCOUNT_ALREADY_BOUND（账号已被关联）；
- MULTIPLE_CANDIDATES（存在多个候选账号）；
- REVIEW_REQUIRED（需要管理员审核）；
- UPSTREAM_UNAVAILABLE（上游服务不可用）；
- ACCOUNT_MAPPING_CONFLICT（账号映射冲突）。

不得将所有错误统一写成“关联失败”。

### 14.11 唯一绑定

同一 application_id + external_user_id 同时最多存在一个有效 BOUND 映射。

已绑定其他统一用户时：

- 不得自动覆盖；
- 进入 CONFLICT；
- 由管理员核实处理；
- 处理过程写审计。

- 其他主要入口包括应用列表、用户管理、身份与子系统映射；
- 顶部概览不重复展示“待审核申请”，避免与待处理事项重复。

### 20.3 接入运行状态与接入异常

“接入运行状态”和“接入异常”在常规桌面宽度下同一行展示：

- 左侧：接入运行状态；
- 右侧：接入异常；
- 窄屏时自动上下堆叠。

接入运行状态按 SSO / TODO / MESSAGE 三行纵向展示，每行分别显示：

- 正常；
- 异常；

### 20.4 接入异常

每条至少显示：

- 应用名称；
- 接入服务类型；
- 最近错误摘要；
- 异常状态。

同一应用如果 SSO / TODO / MESSAGE 中有多个服务异常，应按服务分别计数和展示。

映射冲突、身份异常等业务异常不混入本区域，统一进入“待处理事项”或对应业务管理页面。

无异常时显示“暂无接入异常”。

### 20.5 页面位置与响应式

- 常用管理不再固定放置在页面底部，而是与待处理事项同一行；
- 接入运行状态、接入异常继续位于该行之后；

- 选择“政务用户”时，匹配仅政务（GOV）以及公众及政务（BOTH）的应用；
- 选择“公众及政务”时，仅匹配 BOTH；
- 未选择适用用户时不限制该条件，展示管理端权限范围内的全部应用。

管理端应用列表必须基于纳管应用全量目录进行查询，不得按当前管理员自身用户类别过滤应用。

### 21.2 应用基本信息

详情字段顺序：

1. 应用名称、应用编码；
2. 系统分类、启用状态；

- BIND。

### 21.5 下载接口文件

## 30. 通知公告管理

路由：

- `/admin/announcements`
- `/admin/announcements/:id`

### 30.1 生命周期

- DRAFT（草稿）；
- SCHEDULED（定时发布）；
- PUBLISHED（已发布）；
- WITHDRAWN（已撤回）；
- EXPIRED（已过期）。

### 30.2 功能

支持：

- 新增；
- 保存草稿；
- 立即发布；
- 定时发布；
- 预览；
- 已发布编辑；
- 撤回；
- 按规则删除；
- 正文插图；
- 附件；
- HTML/TXT 导入；

新增公告时必须直接选择发布方式：

- 立即发布：不显示“定时发布时间”字段，保存公告后立即进入 PUBLISHED；
- 定时发布：选择后才显示“定时发布时间”，且必须选择未来时间，保存后进入 SCHEDULED；
- 用户也可以先“保存草稿”，草稿后续编辑时仍可选择立即发布或定时发布。

失效时间采用“失效日期”录入：

- 用户只选择日期，不要求输入具体时分秒；
- 留空表示永久有效；
- 选择日期后，系统统一按该日期当天 23:59:59 作为有效截止时间；
- 定时发布时间必须早于失效时间，避免公告尚未发布即已失效。

### 30.3 页面交互

- “新增公告”位于页面标题右侧；
- 新增公告选择“立即发布”时不显示“定时发布时间”；只有选择“定时发布”后才动态显示该字段；
- 新增公告、DRAFT草稿编辑、SCHEDULED定时公告编辑提供一致的业务字段与发布操作；
- 失效字段名称为“失效日期”，只选择日期；
- 公告标题作为详情入口；
- 管理端公告详情继续在右侧内容区打开，不使用详情弹窗；
- 公告编辑使用编辑弹窗，不通过路由切换到独立编辑页；
- 从列表点击“编辑”时直接打开编辑弹窗，关闭/取消后仍停留在公告列表，不应先跳转公告详情；
- 从公告详情点击“编辑”时打开编辑弹窗，关闭后仍停留在当前详情；
- 新增、DRAFT 草稿编辑、SCHEDULED 定时公告编辑三种场景提供相同的操作集合：取消、预览、保存草稿、立即发布/定时发布；
- DRAFT 草稿编辑时可保存草稿，也可直接立即发布或定时发布；选择定时发布后显示并必填定时发布时间；
- SCHEDULED 定时公告编辑时继续显示“发布方式”，默认选中“定时发布”；可调整正文、基础信息、定时发布时间和失效日期；
- SCHEDULED 定时公告点击“保存草稿”时，取消原定时计划并回到 DRAFT；点击“定时发布”则更新定时计划并保持 SCHEDULED；切换“立即发布”后点击立即发布则转为 PUBLISHED；
- PUBLISHED 已发布公告编辑时不再显示发布方式，点击“保存修改”后直接对当前已发布内容生效；
- WITHDRAWN 已撤回公告允许继续编辑和删除；编辑界面与新增、DRAFT、SCHEDULED保持相同字段排布和操作集合：取消、预览、保存草稿、立即发布/定时发布；
- WITHDRAWN编辑后点击“保存草稿”转为DRAFT；点击“立即发布”转为PUBLISHED；选择未来时间并点击“定时发布”转为SCHEDULED；重新发布后清除原撤回标记；
- EXPIRED 已过期公告不允许编辑，只允许删除；
- 左侧“通知公告管理”保持选中；
- 撤回操作需要确认；
- 删除操作需要二次确认，并明确删除后不可恢复；
- 列表页与公告详情页必须遵循同一状态操作权限：WITHDRAWN 显示“编辑、删除”，其编辑弹窗可继续保存草稿或重新发布；EXPIRED 仅显示“删除”。

## 33. SSO / TODO / MESSAGE 接入

### 33.1 总体原则

每个应用可独立配置：

- SSO；
- TODO；
- MESSAGE。

配置入口唯一：应用列表 → 连接配置。

监控入口唯一：运行监控。

### 33.2 SSO

目标：

- 从门户进入目标子系统；
- 带入必要统一身份信息；
- 子系统自行进行业务授权。

具体协议可按系统能力采用：

- OIDC；
- SAML2；
- CAS/票据；
- Token；
- 自定义适配。

### 33.3 TODO

子系统通过 PUSH 将待办推送门户。

标准接入字段只要求：

- eventId；
- sourceTodoId；
- userId；
- status；
- title。

门户可根据应用配置补充来源应用名称、业务类型和业务跳转地址。

不要求同步：

- priority；
- dueAt / 截止时间；
- sourceRevision；
- terminalAt。

标准状态只接受 PENDING（待处理） / COMPLETED（已处理） / WITHDRAWN（已撤回）。

幂等使用 application + eventId 控制；同一 sourceTodoId 用于识别同一来源待办。终态后不得回退为待处理。门户不主动篡改子系统权威业务状态，也不根据时间自行判断逾期。

### 33.4 MESSAGE

子系统通过 PUSH 推送消息。

必须考虑：

- 应用鉴权；
- eventId；
- sourceMessageId；
- 用户；
- 标题；
- 正文；
- 来源；
- 幂等。

### 33.5 接口规范文件

门户应提供统一接入规范供子系统开发对接。

每个子系统的 Client ID、凭据引用、回调地址等个性参数由应用连接配置维护。

## 36. 核心业务流程

### 36.1 用户端登录

```text
选择公众用户或政务用户
→ 点击“进入系统”
→ 建立对应Mock Portal Session
→ 用户端
```

### 36.2 管理端演示登录

```text
选择“管理账号”
→ 显示固定演示账号 admin
→ 点击“进入管理端”
→ 建立管理员Mock Portal Session
→ 管理端
```

### 36.3 外部用户进入管理端

```text
闽政通/闽政务认证
→ Portal Session
→ 检查门户角色
→ 有管理角色：允许进入管理端
→ 无管理角色：仅普通用户端
```

### 36.4 应用访问

```text
用户点击应用
→ 校验应用启用状态
→ 校验适用用户类别
→ 校验门户入口资格
→ 必要时确认子系统账号关系
→ SSO/跳转
→ 子系统自行判定业务权限
```

### 36.5 REQUEST

```text
提交入口申请
→ PENDING
→ 管理员审核
→ APPROVED / REJECTED
→ APPROVED 后获得门户入口资格
→ 如仍需账号确认则继续
→ 进入应用
```

### 36.6 BIND 内部流程

```text
检查已有映射
→ 已 BOUND：进入
→ 未确认：后台发现候选关系
→ 必要的子系统/上层认证
→ 普通账号：BOUND
→ 高风险账号：REVIEWING
→ 冲突：CONFLICT
```

普通用户侧不展示这一技术过程，只展示结果与下一步。

### 36.7 公告

```text
DRAFT
→ 立即发布：PUBLISHED
→ 设置定时发布：仍保存为 DRAFT + publish_mode=SCHEDULED
→ 到达计划时间：PUBLISHED
PUBLISHED → WITHDRAWN
PUBLISHED + effective_end已到 → 页面派生显示 EXPIRED
```

PUBLISHED 允许按需求规则编辑；SCHEDULED、EXPIRED 为页面派生展示状态，不作为新增永久主状态。

### 36.8 待办/消息

```text
子系统 PUSH
→ 门户幂等接收
→ 按用户聚合
→ 用户查看
→ 业务处理跳回子系统
```

### 36.9 异常日志

```text
OPEN
→ 管理员查看与填写处理说明
→ RESOLVED
```

## 37. 通用交互要求

系统应满足以下通用交互要求：

- 页面能够完成对应业务功能和状态流转；
- 同一业务规则在首页、列表、详情等不同入口保持一致；
- 数据加载、无数据和加载失败应分别展示 Loading、Empty、Error 等明确状态，数据尚未完成加载时不得误显示为空；
- 面向业务用户的界面使用业务语言，不直接暴露内部状态机代码、接口实现术语或技术异常细节；
- 关键提交、撤回、删除、解绑、审核等操作应根据风险提供必要的二次确认；
- 操作成功后提供明确结果反馈，操作失败时提供可理解的错误原因和下一步建议；
- 列表无数据时使用统一空状态表达，并提供明确的无数据说明；
- 列表或表格中的文本因列宽限制被省略时，鼠标悬浮应显示该字段完整内容；未发生截断时不重复显示浮层，操作按钮、开关、状态标签等非纯文本内容不强制使用该提示；
- 详情、编辑、弹窗及返回行为应保持业务上下文连续，避免因页面跳转造成状态或导航上下文丢失；
- 具体视觉设计、组件选型、字号、颜色、间距、图标及视觉验收标准由配套设计规范定义，不在本文中重复约束。

## 39. 数据隔离与安全

### 39.1 用户数据隔离

用户端：

- 待办只看本人；
- 消息只看本人；
- 公告按发布范围；
- 应用按用户类别、适用范围、入口资格和映射结果；
- 我的申请只看本人。

管理端根据角色权限访问管理数据。

### 39.2 凭据保护

不得记录：

- 外部身份密码；
- 子系统明文密码；
- OTP；
- Token；
- password_hash。

敏感连接凭据使用环境变量/凭据引用等方式管理。

### 39.3 后端鉴权

高风险写操作必须服务端二次鉴权，不能只依赖前端隐藏按钮。

### 39.4 审计

关键动作需记录：

- 操作人；
- 对象；
- 动作；
- 结果；
- 时间；
- 请求ID；
- 必要上下文。

## 40. 非功能性要求

### 40.1 可用性

- 常用操作路径清晰；
- 用户侧尽量使用业务语言；
- 不向普通用户暴露底层状态机和接口实现术语；
- 同一业务在不同入口遵循相同的权限、状态和数据规则。

### 40.2 业务一致性

- 业务术语统一；
- 状态枚举与状态含义统一；
- 权限判断和数据范围规则统一；
- 同一业务动作的前置校验和结果语义统一。

### 40.3 可扩展性

- RBAC 支持未来自定义角色；
- 数据范围支持未来扩展；
- 应用支持多种 SSO；
- 接入配置支持多子系统差异；
- 用户索引允许未来扩展身份来源。

## 44. 原型交付与实施约束

本项目当前交付定位为**高保真、可演示、业务闭环完整、接口设计可落地的原型系统**，不以生产部署和真实外部系统联调作为本轮验收目标。

- 公众用户、政务用户登录继续以闽政通/闽政务业务语义进行模拟，管理账号采用门户本地管理账号的演示流程；本轮不要求真实接入闽政通/闽政务。
- SSO、TODO、MESSAGE、子系统账号确认均允许使用 Mock Provider/本地模拟接收器完成演示，但字段、状态、鉴权、幂等、错误码、时间格式、身份定位及权限边界必须按可实施的技术规范设计。
- 约43个业务子系统的逐系统真实联调不属于本轮原型交付范围；应用目录、连接配置、接入状态和演示数据应能够覆盖典型接入场景。
- “下载接口文件”必须输出可被 Swagger / Postman 等工具识别的 OpenAPI 3.x 文档，并与当前可演示的本地 Mock 接口或明确标注的目标接入契约保持一致；不得下载空壳、占位或与页面配置不一致的文件。
- SSO/TODO/MESSAGE 连接配置必须体现实际工程需要的核心参数和业务约束；对于真实 Secret、Token、私钥等敏感信息，只保留安全引用/示例值，不在原型代码仓库中保存真实凭据。
- 数据库不以生产级重构、全量 Migration 和生产切换为当前验收门槛；如为演示需要持久化数据，只做与当前业务模型一致的最小数据结构和演示数据对齐。
- Mock 数据必须覆盖正常、异常、待审核、冲突、停用等关键场景，并保证操作后的状态变化符合当前需求和状态机。
- 原型页面不得把 Mock 结果表述为已经完成真实外部联调；开发文档中应明确“演示模拟”和“目标技术契约”的边界。
- 当前阶段优先完成浏览器人工验收、业务链路验收、接口文档可用性检查以及 test/build 回归，验收通过后冻结演示版本。

## 45. 验收原则

### 45.0 原型验收范围

本轮验收以**人工浏览器操作为主、自动化测试与构建为辅**。验收对象包括页面显示、查询与分页、弹窗/详情、状态驱动操作、完整业务链路、Mock 数据变化、接口文件下载和接口契约可用性。

本轮不以真实闽政通/闽政务接入、43个子系统逐一联调、生产数据库切换或生产部署作为通过条件。


### 45.1 身份与权限

- 闽政通/闽政务两类用户端身份来源识别正确；
- LOCAL 仅作为门户本地管理认证方式，不作为第三类用户端身份；
- 用户类别、认证类型与门户角色不混用；
- 无管理角色用户不能进入管理端；
- LOCAL 可独立登录；
- 默认角色仅超级管理员和门户管理员；
- 子系统业务权限不进入门户角色管理。

### 45.2 用户端

- 数据按当前用户隔离；
- 我的应用只显示已可使用应用；
- 其它应用显示结果和下一步，不暴露技术过程；
- 应用申请闭环；
- 账号异常/未开户/停用有明确结果；
- 待办、消息、公告正常展示；
- Loading 不闪 Empty。

### 45.3 管理端

- 应用、用户、角色、组织、字典、映射、配置可按权限管理；
- 应用连接配置入口唯一；
- 启用状态维护正确生效；
- 身份映射详情分区和分页正确；
- 日志字段按类型展示；
- 异常日志可闭环；
- 运行监控只承担接入健康查看。

### 45.4 交互验收

- 页面功能入口可正常使用；
- Loading / Empty / Error 状态语义正确；
- 详情、编辑、提交、撤回、删除等操作遵循已确认业务规则；
- 页面不向业务用户暴露内部状态机代码、研发实现术语或不必要的技术状态；
- 视觉表现按照配套设计规范进行验收，本文重点验收业务功能、状态、权限、流程及交互结果。

### 45.5 安全

- 明文密码不落库；
- password_hash 不返回前端；
- OTP/Token 不写日志；
- 高风险操作服务端鉴权；
- 映射冲突不得自动覆盖；
- 关键操作可追溯。
