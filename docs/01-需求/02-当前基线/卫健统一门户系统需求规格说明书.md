## 2. 建设背景与目标

卫健统一门户用于在闽政通、闽政务等上层权威身份体系与多个卫健业务子系统之间建立统一访问入口。

建设目标：

- 提供统一登录入口；
- 承接公众、政务及门户本地三类身份；
- 建立统一用户索引，但不重复建设完整公众/政务身份库；
- 聚合用户可访问的业务应用；
- 支持应用入口申请、账号确认及访问前校验；
- 聚合待办、消息和门户公告；
- 为管理员提供应用、用户、角色、组织、字典、映射、配置、日志及接入健康管理；
- 保持门户入口权限与子系统业务权限严格分离；
- 为各业务子系统提供统一 SSO / TODO / MESSAGE 接入规范；
- 首期优先形成可演示、可闭环、可继续联调的统一门户能力。

## 3. 系统定位

### 3.1 总体关系

```text
闽政通 ──→ 公众用户 CITIZEN ┐
闽政务 ──→ 政务用户 GOV    ├─→ 卫健统一门户 ─→ 业务子系统
门户本地 ─→ 本地用户 LOCAL  ┘
```

卫健统一门户位于身份来源与业务子系统之间，承担“统一身份承接 + 门户入口授权 + 应用聚合 + 公共事务聚合 + 管理支撑”。

### 3.2 门户不是

门户不是：

- 闽政通/闽政务的替代身份平台；
- 子系统统一用户主库；
- 子系统统一角色中心；
- 子系统统一菜单权限中心；
- 子系统统一数据权限中心；
- 子系统业务审批平台；
- 复杂 APM、服务器监控或链路追踪平台。

### 3.3 总体原则

> 统一身份承接 + 门户入口授权 + 子系统分布式业务授权。

门户决定“用户能否从门户看到、申请、进入某个应用”，子系统决定“用户进入后拥有什么业务角色、菜单、数据和操作权限”。

## 4. 建设范围与责任边界

### 4.1 上层身份平台负责

闽政通负责公众用户权威身份，闽政务负责政务用户权威身份。

上层平台负责：

- 正式身份注册/开通；
- 实名认证；
- 外部账号安全；
- 外部身份核心状态；
- 扫码、手机号验证码等上层认证能力；
- 如具备条件，可提供人脸等强身份核验能力。

门户不自行保存公众/政务用户人脸模板。

### 4.2 统一门户负责

门户负责：

- 统一登录入口；
- 闽政通/闽政务认证结果承接；
- PORTAL_LOCAL 本地管理身份；
- Portal Session；
- 统一用户索引；
- 用户类别识别；
- 门户用户启用状态；
- 门户角色和 MENU / PAGE / ACTION 权限；
- 本地管理账号生命周期；
- 应用目录；
- 应用适用用户规则；
- DIRECT / BIND / REQUEST 入口模式；
- 应用访问申请；
- 应用入口授权；
- 子系统账号映射；
- 映射审核、异常和冲突处理；
- 待办、消息聚合；
- 门户公告；
- 组织索引；
- 字典与配置；
- SSO / TODO / MESSAGE 接入配置；
- 接入健康查看；
- 登录、访问、操作、接口、异常日志。

### 4.3 业务子系统负责

子系统负责：

- 子系统账号本体；
- 子系统开户注册；
- 子系统账号启停；
- 子系统业务角色；
- 子系统菜单权限；
- 子系统数据权限；
- 子系统业务审批；
- 业务状态；
- 高权限账号管理；
- 子系统自身认证/授权页；
- 子系统已有账号真实性；
- 子系统原登记手机号 OTP 或账号校验接口（如提供）。

### 4.4 首期不纳入范围

首期不建设：

- 公众用户完整生命周期管理；
- 政务人员完整生命周期管理；
- 外部用户密码管理；
- 面向公众开放 PORTAL_LOCAL 自助注册；
- 子系统业务角色统一维护；
- 子系统菜单/数据权限集中维护；
- 门户替子系统直接创建业务账号；
- 复杂组织数据权限；
- 复杂应用级数据范围；
- 收藏应用；
- 复杂运维 APM；
- 短信费用统计。

## 5. 核心术语

| 术语 | 含义 |
|---|---|
| 身份来源 | MINZHENGTONG / MINZHENGWU / PORTAL_LOCAL |
| 用户类别 | CITIZEN / GOV / LOCAL |
| 门户角色 | SUPER_ADMIN / PORTAL_ADMIN / 后续自定义门户角色 |
| Portal Session | 统一门户登录后的会话 |
| 应用入口资格 | 用户是否可从统一门户进入某应用 |
| 子系统业务权限 | 用户进入子系统后由子系统判定的业务权限 |
| DIRECT | 满足适用范围后无需门户账号映射即可进入 |
| BIND | 进入前需要确认统一用户与子系统账号关系 |
| REQUEST | 进入前需要先取得门户应用入口资格 |
| BOUND | 子系统账号映射已有效确认 |
| TODO | 子系统推送至门户的待办 |
| MESSAGE | 子系统或门户产生的消息 |
| SSO | 门户到子系统的单点/统一跳转能力 |

## 6. 身份来源、用户类别与门户角色

三者必须严格分离。

### 6.1 身份来源与用户类别

| 身份来源 | 用户类别 | 权威主体 | 首期主要入口 |
|---|---|---|---|
| MINZHENGTONG / 闽政通 | CITIZEN / 公众用户 | 闽政通 | 用户端 |
| MINZHENGWU / 闽政务 | GOV / 政务用户 | 闽政务 | 用户端；有管理角色时可进入管理端 |
| PORTAL_LOCAL / 门户本地 | LOCAL / 门户本地用户 | 卫健统一门户 | 管理端 |

规则：

- 身份来源不是角色；
- 用户类别不是角色；
- LOCAL 不要求绑定闽政通/闽政务；
- LOCAL 不自动等于管理员；
- CITIZEN/GOV 若被分配门户管理角色，也可进入管理端；
- 外部身份成为管理员后仍保持原身份来源和用户类别，不复制成本地用户。

### 6.2 统一用户索引

门户保存最小必要统一索引，例如：

- unified_user_id；
- account；
- name；
- user_type；
- identity_source；
- org_id；
- org_name；
- portal_status；
- first_login_at；
- last_login_at；
- created_at；
- updated_at。

公众用户不强制所属组织；不得制造“公众服务”等虚假组织。

政务用户组织以闽政务实际返回为准。

LOCAL 所属组织可空。

### 6.3 跨身份源关系

CITIZEN 与 GOV 不默认自动合并为同一自然人。

如未来需要跨源关联：

1. 优先使用稳定权威跨源唯一标识；
2. 无稳定标识时，只能产生候选关系；
3. 必须经过上层重新认证或更强身份核验；
4. 不以姓名作为唯一身份判断；
5. 姓名 + 手机号仅能辅助候选匹配；
6. 关联过程保留证据与审计。

## 7. 门户本地账号

### 7.1 使用场景

门户本地账号主要解决平台维护人员没有闽政通或闽政务身份时的独立管理端登录。

### 7.2 账号字段

至少包括：

- 用户ID；
- 登录账号；
- 姓名；
- 手机号/邮箱（可选）；
- 启用状态；
- 门户角色；
- must_change_password；
- failed_login_count；
- locked_until；
- password_updated_at；
- last_login_at。

凭证单独维护：

- username；
- password_hash；
- password_algorithm；
- must_change_password；
- failed_login_count；
- locked_until；
- password_updated_at。

禁止：

- 明文保存密码；
- API 返回 password_hash；
- 将初始超级管理员固定密码写入源码或 Git。

### 7.3 管理规则

- 仅超级管理员可创建本地管理用户；
- 可编辑门户资料；
- 可启停；
- 可分配门户角色；
- 可重置密码；
- 可解除锁定；
- 不开放公众自助注册；
- 没有管理角色的 LOCAL 不得进入管理端。

## 8. 门户角色与权限模型

### 8.1 默认角色

首期只预置：

| 角色 | 编码 | 定位 |
|---|---|---|
| 门户超级管理员 | SUPER_ADMIN | 最高门户管理权限 |
| 门户管理员 | PORTAL_ADMIN | 日常门户维护 |

预计实际维护人员较少，因此首期不预置应用管理员、公告管理员、审计管理员、集成管理员等大量细分角色。

### 8.2 权限模型

门户 RBAC 支持：

```text
菜单 MENU
  └─ 页面 PAGE
       └─ 操作 ACTION
```

首期两个默认管理角色数据范围按 ALL_PORTAL 处理。

SELF / ORG / ORG_AND_CHILDREN / ASSIGNED_APPS 等数据范围作为后续扩展，不作为首期复杂配置项。

### 8.3 超级管理员

默认拥有：

- 全部管理端菜单；
- 全部页面；
- 全部操作；
- 用户及本地账号管理；
- 角色权限管理；
- 组织、字典、配置；
- 应用、公告、映射、监控、日志；
- 管理员授权；
- 本地用户密码重置；
- 关键配置维护。

系统必须保护最后一个有效超级管理员账号和超级管理权限。

### 8.4 门户管理员

默认承担日常维护：

- 管理首页；
- 通知公告；
- 应用目录；
- 应用访问申请；
- 子系统账号开通申请状态（如启用）；
- 运行监控；
- 身份与子系统映射；
- 用户查询及必要门户侧维护；
- 组织；
- 字典；
- 日志审计。

高风险操作可只允许超级管理员：

- 创建/删除本地管理账号；
- 重置其他管理员密码；
- 角色权限配置；
- 超级管理员授权；
- 删除关键配置。

### 8.5 子系统权限隔离

门户角色不得：

- 创建子系统业务角色；
- 修改子系统业务角色；
- 分配子系统菜单；
- 分配子系统数据权限；
- 代替子系统完成业务审批。

## 9. 用户端与管理端关系

“用户端”和“平台管理端”是两个使用入口，不是两个用户类别。

### 9.1 用户端

首期主要面向：

- CITIZEN；
- GOV。

### 9.2 管理端

进入管理端必须拥有有效门户管理角色。

可来源：

- LOCAL + 门户管理角色；
- GOV + 门户管理角色；
- CITIZEN + 门户管理角色（能力保留，非首期主要场景）。

### 9.3 端切换

同一 Portal Session 下，若当前用户同时具备用户端和管理端访问资格，可提供“用户端门户 / 平台管理端”切换，不要求重复登录。

## 11. 统一登录

### 11.1 路由

统一登录路由：`/login`。

用户端和管理端不建设两套独立登录页。

### 11.2 登录入口

提供三类入口：

- 公众用户 → 闽政通；
- 政务用户 → 闽政务；
- 管理账号 → PORTAL_LOCAL。

### 11.3 公众用户

- 支持扫码/手机号等上层能力；
- 认证成功建立/更新统一用户索引；
- 创建 Portal Session；
- 默认进入用户端。

### 11.4 政务用户

- 支持扫码/手机号/上层免登等能力；
- 创建 Portal Session；
- 默认进入用户端；
- 有有效门户角色时可进入或切换管理端。

### 11.5 管理账号

正式能力：

- 用户账号；
- 登录密码；
- 验证码；
- 登录按钮。

正式环境校验：

- 必须为 LOCAL；
- 账号启用；
- 未锁定；
- 密码正确；
- 拥有有效管理角色；
- 首次登录可强制修改密码。

### 11.6 登录页视觉与交互

- 去掉“欢迎使用统一门户”；
- 登录区域使用白色背景；
- 身份切换文字不过大；
- “公众用户 / 政务用户 / 管理账号”三项身份页签文字字重统一为 500，避免过重；
- 身份页签与登录区域顶部之间在现有基础上增加 10px 间距；
- Tab 下划线宽度与文字匹配；
- 扫码/手机号使用紧凑切换；
- 页面底部显示“卫健XC统一门户 · 由中电福富提供技术支持”；
- 公众/政务可保留“尚未注册？立即注册 | 忘记密码”，跳转对应上层平台；
- 管理账号不使用公众/政务滑块认证；
- 管理账号登录区域不展示“原型演示、演示验证码、默认演示账号、密码/验证码可任意填写”等研发/演示说明文案；A阶段Mock行为仅作为内部实现存在，不向用户解释。

### 11.7 二维码交互

原型可模拟：

- 二维码登录不显示额外登录按钮；
- 提示“请使用闽政通扫一扫登录”或“请使用闽政务扫一扫登录”；
- 二维码倒计时；
- 过期时保留二维码并叠加遮罩；
- 点击过期区域刷新；
- 避免多层重复提示。

真实环境以外部身份平台接口能力为准。

### 11.8 Portal Session

三类认证完成后统一建立 Portal Session。

Session 建立后根据用户类别和门户角色决定可访问端。

## 12. 认证结果页

路由：`/auth/result`。

状态：

- SUCCESS；
- FAILURE；
- DISABLED；
- LOCKED；
- NO_PERMISSION；
- UPSTREAM_ERROR；
- SESSION_ERROR。

页面显示：

- 认证来源；
- 结果状态；
- 请求ID（存在时）；
- 状态说明；
- 下一步操作。

操作：

- SUCCESS → 进入目标端；
- NO_PERMISSION → 有普通用户 Session 时返回用户端；
- FAILURE / UPSTREAM_ERROR / SESSION_ERROR → 重新登录；
- DISABLED / LOCKED → 返回登录并提示联系管理员。

展示顺序：

1. 我的待办；

## 14. 应用中心

路由：`/portal/apps/all`。

### 14.1 分组

应用中心分为：

- 我的应用；
- 其它应用。

“我的应用”只展示当前已经满足访问条件的应用。

“其它应用”只展示当前用户可见但仍需申请、账号确认、等待处理或异常处理的应用。

不得向普通用户展示无适用范围的全部后台应用目录。

### 14.2 内部访问模式

门户内部支持：

- DIRECT；
- BIND；
- REQUEST。

这些属于内部访问控制模型，不要求普通用户理解。

### 14.3 DIRECT

满足：

- 应用已启用；
- 用户类别适用；
- 应用入口允许；

即可直接进入后续 SSO/跳转。

### 14.4 REQUEST

REQUEST 用于控制门户入口资格。

状态：

- PENDING；
- APPROVED；
- REJECTED；
- WITHDRAWN；
- EXPIRED。

申请通过只代表“获得门户入口资格”，不代表获得子系统业务权限。

### 14.5 BIND

BIND 内部支持：

- AUTO；
- SELF；
- REVIEW；
- ADMIN。

用户侧不显示这些代码。

### 14.6 用户侧结果导向交互

用户侧以“当前结果 + 下一步操作”为核心。

可见操作收敛为：

- 进入应用；
- 申请使用；
- 完成账号确认；
- 查看申请；
- 查看进度；
- 继续处理；
- 查看原因；
- 重新处理。

可见状态使用业务化文案：

- 待申请；
- 申请处理中；
- 申请未通过；
- 需确认账号；
- 待继续处理；
- 处理中；
- 处理失败；
- 账号异常；
- 账号不可用。

不得直接把 BIND、VERIFYING、REVIEWING、CONFLICT 等代码暴露给普通用户。

### 14.7 已有历史账号

当需要历史账号、密码、验证码或子系统自身认证时：

1. 门户先判断是否已有有效映射；
2. 如可通过可信唯一标识唯一确认，可在后台直接完成；
3. 如需用户认证，门户显示“需要完成账号确认”；
4. 用户点击“前往子系统确认”；
5. 历史账号、密码、验证码等在目标子系统输入；
6. 门户不采集这些凭据；
7. 用户完成后返回门户；
8. 门户通过回调/标准接口/重新检测更新结果。

### 14.8 未检测到子系统账号

显示：

> 需要开通账号。

默认操作：

- 前往子系统开通；
- 完成后重新检测。

规则：

- 门户不直接创建子系统账号；
- 开户规则由子系统决定；
- 只有子系统提供标准开户申请接口时，门户才可承接申请提交与状态回显。

### 14.9 高权限账号

高权限账号可在完成必要确认后进入 REVIEWING，待门户管理员审核。

用户侧只显示“处理中/账号确认已提交”。

### 14.10 冲突和失败

至少区分：

- ACCOUNT_NOT_FOUND；
- INVALID_CREDENTIALS；
- OTP_INVALID；
- OTP_EXPIRED；
- ACCOUNT_DISABLED；
- ACCOUNT_ALREADY_BOUND；
- MULTIPLE_CANDIDATES；
- REVIEW_REQUIRED；
- UPSTREAM_UNAVAILABLE；
- ACCOUNT_MAPPING_CONFLICT。

不得将所有错误统一写成“关联失败”。

### 14.11 唯一绑定

同一 application_id + external_user_id 同时最多存在一个有效 BOUND 映射。

已绑定其他统一用户时：

- 不得自动覆盖；
- 进入 CONFLICT；
- 由管理员核实处理；
- 处理过程写审计。

## 16. 待办任务

### 16.4 详情

待办详情不使用网格字段布局，参考通知公告详情的信息层级展示；首页“我的待办”打开的详情与“待办任务”列表打开的详情必须复用同一详情内容组件，保证信息、顺序和样式完全一致：

1. 第1行：待办标题，作为详情主标题单独显示；
2. 元信息区域采用两行两列：第1行显示来源应用、业务类型；第2行显示接收时间、状态；
3. 四个元信息分别增加 TDesign 语义图标；
4. 各元信息采用“标签：值”的单行形式，例如“来源应用：XXX”“业务类型：XXX”，标签和值不得上下换行；
5. 元信息区域下方增加横向分隔线；
6. 分隔线下直接显示待办说明正文，不再显示“待办说明”标题文字。

详情不再显示“源待办ID”。该字段仅作为系统内部来源待办标识保留。

不展示：

- 优先级；
- 截止时间；
- 逾期信息；
- 来源版本；
- 终态时间。

### 16.5 状态与操作

门户待办标准状态首期只保留：

- PENDING：待处理；
- COMPLETED：已处理；
- WITHDRAWN：已撤回。

规则：

- 仅 PENDING 显示“去处理”；
- 门户不根据时间自动产生“逾期/过期”状态；
- 不同步来源系统截止时间；
- 不要求来源系统提供优先级；
- 不要求来源系统提供来源版本；
- 业务处理仍进入目标子系统；
- “去处理”前继续校验应用启用状态、入口资格和账号关系；
- 来源系统推送终态后，门户只同步状态，不在门户内执行业务审批。

排序：待处理优先，其余按接收时间近到远。

## 20. 管理首页

路由：`/admin/home`。

面向有门户管理角色的用户，定位为“门户管理工作台”。首页主要回答四类问题：当前纳管规模、当前待处理事项、接入服务是否正常、最近有哪些接入异常。

### 20.1 顶部概览指标

顶部只保留四个同层级核心指标：

| 指标 | 统计口径 | 点击去向 |
|---|---|---|
| 纳管应用 | 当前统一应用目录中的应用总数 | 应用列表 |
| 启用应用 | 当前启用状态的应用数量 | 应用列表 |
| 门户用户 | 已建立统一用户索引的用户数量 | 用户管理 |
| 接入异常 | 已配置并运行异常的 SSO / TODO / MESSAGE 服务数量之和 | 运行监控 |

视觉规则：

- 四个指标卡保持当前门户轻量卡片风格，不增加阴影；
- 每个指标增加语义图标，图标使用 TDesign 图标库；
- 卡片采用“左侧图标 + 右侧文字”的横向布局；
- 右侧只保留两行：第1行指标名称、第2行指标值；
- 去掉“统一应用目录、当前启用、已建立统一用户索引、已配置服务运行异常”等第三行辅助说明；
- 四个指标图标均必须显示浅色背景块，不能只显示单独图标或仅有图标颜色；
- 图标背景使用轻量语义色，不改变现有 13px 文字规范；
- 建议语义：纳管应用=应用图标、启用应用=成功/启用图标、门户用户=用户图标、接入异常=异常图标。

业务规则：

- 不再显示“正常应用 / 异常应用”综合指标；
- 不对应用生成额外综合运行状态；
- “接入异常”按服务维度统计，一个应用可同时产生多个异常服务；
- “未配置 / 停用”不计入接入异常。

### 20.2 待处理事项与常用管理

“待处理事项”和“常用管理”在常规桌面宽度下同一行展示：

- 左侧“待处理事项”为主要区域，宽度大于右侧；
- 右侧“常用管理”为快捷入口区域；
- 两个区块标题只显示标题本身，不再显示“按当前账号权限显示”“快速进入常用管理模块”等辅助提示；
- 窄屏时允许自动上下堆叠。

待处理事项包括：

- 应用访问申请；
- 账号开通申请；
- 账号确认审核；
- 映射异常；
- 异常日志；
- 待发布公告。

待处理事项卡片规则：

- 保持当前文字层级和字号；
- 所有待处理事项统一使用同一种浅灰背景，不再按事项类型使用多种底色；
- 背景仅用于形成工作台分区层次，不作为状态判断依据；
- 有待处理数量时数字使用异常/提醒色，数量为 0 时使用普通样式；
- 点击进入对应管理页面。

常用管理规则：

- 使用“小图标 + 标题 + 简短说明”的紧凑入口；
- 图标优先使用 TDesign 图标库；
- 采用两列紧凑布局，避免大卡片占据过多纵向空间；
- 公告快捷入口由“通知公告管理”调整为“新增公告”；
- 点击“新增公告”后进入“通知公告管理”模块，并直接打开“新增公告”弹窗；
- 其他主要入口保留应用列表、用户管理、身份与子系统映射；
- 顶部概览不再重复展示“待审核申请”，避免与待处理事项重复。

### 20.3 接入运行状态与接入异常

“接入运行状态”和“接入异常”在常规桌面宽度下同一行展示：

- 左侧：接入运行状态；
- 右侧：接入异常；
- 窄屏时自动上下堆叠。

接入运行状态按 SSO / TODO / MESSAGE 三行纵向展示，每行分别显示：

- 正常；
- 异常；
- 未配置/停用。

该区域只承担接入健康摘要，点击进入运行监控查看应用级明细。

### 20.4 接入异常

展示最近的异常接入服务，按最近检测时间近到远排序。

每条至少显示：

- 应用名称；
- 接入服务类型；
- 最近错误摘要；
- 异常状态。

同一应用如果 SSO / TODO / MESSAGE 中有多个服务异常，应按服务分别计数和展示。

映射冲突、身份异常等业务异常不混入本区域，统一进入“待处理事项”或对应业务管理页面。

无异常时显示“暂无接入异常”。

### 20.5 页面位置与响应式

- 常用管理不再固定放置在页面底部，而是与待处理事项同一行；
- 接入运行状态、接入异常继续位于该行之后；
- 常用管理按当前账号权限动态显示，不替代左侧正式菜单；
- 桌面宽度不足时，“待处理事项 / 常用管理”自动上下排列；
- 管理首页不建设复杂运行监控图表，不展示服务器资源、链路追踪等 APM 信息；详细接入健康统一进入运行监控。

## 21. 应用管理

列表建议包含：

- 适用用户类别；
- 启用状态；

操作：

- 编辑；
- 连接配置。

启用状态直接使用 TDesign 默认无文字 Switch，不在操作列重复提供“启用/停用”。

### 21.2 应用基本信息

详情字段顺序：

1. 应用名称、应用编码；
2. 系统分类、启用状态；
3. 用户类别、创建时间；
4. 运行状态；
5. 入口地址；
6. 说明。

统一将属于启停语义的“状态”命名为“启用状态”。

### 21.3 应用访问模式配置

应用可配置：

- DIRECT；
- BIND；
- REQUEST。

REQUEST 可进一步配置申请通过后：

- DIRECT；
- BIND。

BIND 内部可配置账号处理模式：

- AUTO；
- SELF；
- REVIEW；
- ADMIN。

这些配置属于管理端，不直接暴露给普通用户。

### 21.4 连接配置

连接配置不建立独立一级菜单。

入口：应用列表 → 连接配置。

配置类型：

- SSO；
- TODO；
- MESSAGE。

配置内容按接入类型显示：

- 启用状态；
- 接入方式/协议；
- 服务地址；
- Client ID 等公开参数；
- 字段映射；
- 凭据引用；
- 备注。

敏感密钥不直接展示在页面或日志中，优先保存凭据引用。

连接信息展示列统一为：

- 接入类型；
- 接入方式；
- 配置状态；
- 启用状态。

第一次打开尚未初始化时，可初始化三类基础配置记录。

### 21.5 下载接口文件

“下载接口文件”为门户级公共接入规范，不属于单条应用行级操作。

应覆盖：

- SSO；
- TODO；
- MESSAGE；
- 标准字段；
- 请求/响应；
- 状态映射；
- 鉴权/幂等要求。

## 30. 通知公告管理

路由：

- `/admin/announcements`
- `/admin/announcements/:id`

### 30.1 生命周期

- DRAFT；
- SCHEDULED；
- PUBLISHED；
- WITHDRAWN；
- EXPIRED。

### 30.2 功能

支持：

- 新增；
- 保存草稿；
- 立即发布；
- 定时发布；
- 预览；
- 已发布编辑；
- 撤回；
- 按规则删除；
- 正文插图；
- 附件；
- HTML/TXT 导入；
- DOCX 正文导入作为目标能力；
- DOC 不作为支持格式。

新增公告时必须直接选择发布方式：

- 立即发布：不显示“定时发布时间”字段，保存公告后立即进入 PUBLISHED；
- 定时发布：选择后才显示“定时发布时间”，且必须选择未来时间，保存后进入 SCHEDULED；
- 用户也可以先“保存草稿”，草稿后续编辑时仍可选择立即发布或定时发布。

失效时间采用“失效日期”录入：

- 用户只选择日期，不要求输入具体时分秒；
- 留空表示永久有效；
- 选择日期后，系统统一按该日期当天 23:59:59 作为有效截止时间；
- 定时发布时间必须早于失效时间，避免公告尚未发布即已失效。

### 30.3 页面交互

- “新增公告”位于页面标题右侧；
- 新增公告选择“立即发布”时不显示“定时发布时间”；只有选择“定时发布”后才动态显示该字段；
- 新增公告、DRAFT草稿编辑、SCHEDULED定时公告编辑共用同一发布区域布局；
- 默认立即发布时：“发布方式”占50%宽度，“失效日期”占50%宽度；
- 切换定时发布后：“发布方式”占25%、“定时发布时间”占25%、“失效日期”仍占50%，失效日期宽度保持不变；
- 窄屏时允许按响应式布局自动换行；
- 失效字段名称统一为“失效日期”，日期组件不显示时间选择；
- 公告标题作为详情入口；
- 管理端公告详情继续在右侧内容区打开，不使用详情弹窗；
- 公告编辑统一使用 TDesign Dialog，不再通过路由切换到右侧“编辑页”；
- 从列表点击“编辑”时直接打开编辑弹窗，关闭/取消后仍停留在公告列表，不应先跳转公告详情；
- 从公告详情点击“编辑”时打开编辑弹窗，关闭后仍停留在当前详情；
- 新增、DRAFT 草稿编辑、SCHEDULED 定时公告编辑三种场景必须保持相同的表单排布和 Footer 操作结构：取消、预览、保存草稿、立即发布/定时发布；
- DRAFT 草稿编辑时可保存草稿，也可直接立即发布或定时发布；选择定时发布后显示并必填定时发布时间；
- SCHEDULED 定时公告编辑时继续显示“发布方式”，默认选中“定时发布”；可调整正文、基础信息、定时发布时间和失效日期；
- SCHEDULED 定时公告点击“保存草稿”时，取消原定时计划并回到 DRAFT；点击“定时发布”则更新定时计划并保持 SCHEDULED；切换“立即发布”后点击立即发布则转为 PUBLISHED；
- PUBLISHED 已发布公告编辑时不再显示发布方式，点击“保存修改”后直接对当前已发布内容生效；
- WITHDRAWN 已撤回公告允许继续编辑，保存后仍保持 WITHDRAWN，同时允许删除；
- EXPIRED 已过期公告不允许编辑，只允许删除；
- 左侧“通知公告管理”保持选中；
- 公告详情正文区域默认最小高度 350px；即使正文只有一两行，标题信息区下方分隔线与附件区上方分隔线之间仍保持至少 350px 的正文承载区域；
- 撤回确认使用 Warning；
- 删除确认使用 Danger；
- 删除文案明确不可恢复；
- 列表页与公告详情页必须遵循同一状态操作权限：WITHDRAWN 显示“编辑、删除”，EXPIRED 仅显示“删除”。

## 33. SSO / TODO / MESSAGE 接入

### 33.1 总体原则

每个应用可独立配置：

- SSO；
- TODO；
- MESSAGE。

配置入口唯一：应用列表 → 连接配置。

监控入口唯一：运行监控。

### 33.2 SSO

目标：

- 从门户进入目标子系统；
- 带入必要统一身份信息；
- 子系统自行进行业务授权。

具体协议可按系统能力采用：

- OIDC；
- SAML2；
- CAS/票据；
- Token；
- 自定义适配。

### 33.3 TODO

子系统通过 PUSH 将待办推送门户。

标准接入字段只要求：

- eventId；
- sourceTodoId；
- userId；
- status；
- title。

门户可根据应用配置补充来源应用名称、业务类型和业务跳转地址。

不要求同步：

- priority；
- dueAt / 截止时间；
- sourceRevision；
- terminalAt。

标准状态首期只接受 PENDING / COMPLETED / WITHDRAWN。

幂等使用 application + eventId 控制；同一 sourceTodoId 用于识别同一来源待办。终态后不得回退为待处理。门户不主动篡改子系统权威业务状态，也不根据时间自行判断逾期。

### 33.4 MESSAGE

子系统通过 PUSH 推送消息。

必须考虑：

- 应用鉴权；
- eventId；
- sourceMessageId；
- 用户；
- 标题；
- 正文；
- 来源；
- 幂等。

### 33.5 接口规范文件

门户应提供统一接入规范供子系统开发对接。

每个子系统的 Client ID、凭据引用、回调地址等个性参数由应用连接配置维护。

## 36. 核心业务流程

### 36.1 用户端登录

```text
闽政通/闽政务认证
→ 建立或更新统一用户索引
→ 创建 Portal Session
→ 用户端
```

### 36.2 管理端本地登录

```text
输入本地账号/密码
→ 校验启用/锁定
→ 校验密码
→ 检查门户管理角色
→ 首次改密（如需要）
→ 建立 Portal Session
→ 写登录日志
→ 管理端
```

### 36.3 外部用户进入管理端

```text
闽政通/闽政务认证
→ Portal Session
→ 检查门户角色
→ 有管理角色：允许进入管理端
→ 无管理角色：仅普通用户端
```

### 36.4 应用访问

```text
用户点击应用
→ 校验应用启用状态
→ 校验适用用户类别
→ 校验门户入口资格
→ 必要时确认子系统账号关系
→ SSO/跳转
→ 子系统自行判定业务权限
```

### 36.5 REQUEST

```text
提交入口申请
→ PENDING
→ 管理员审核
→ APPROVED / REJECTED
→ APPROVED 后获得门户入口资格
→ 如仍需账号确认则继续
→ 进入应用
```

### 36.6 BIND 内部流程

```text
检查已有映射
→ 已 BOUND：进入
→ 未确认：后台发现候选关系
→ 必要的子系统/上层认证
→ 普通账号：BOUND
→ 高风险账号：REVIEWING
→ 冲突：CONFLICT
```

普通用户侧不展示这一技术过程，只展示结果与下一步。

### 36.7 公告

```text
DRAFT
→ 立即发布：PUBLISHED
→ 定时发布：SCHEDULED → 到时 PUBLISHED
→ WITHDRAWN / EXPIRED
```

PUBLISHED 允许编辑。

### 36.8 待办/消息

```text
子系统 PUSH
→ 门户幂等接收
→ 按用户聚合
→ 用户查看
→ 业务处理跳回子系统
```

### 36.9 异常日志

```text
OPEN
→ 管理员查看与填写处理说明
→ RESOLVED
```

## 37. 全局 UI 与交互规范

### 37.1 技术与设计基线

- Vue 3；
- Vite；
- TDesign Vue Next；
- 参考 office-house 的信息密度与交互风格；
- 业务样式集中维护，避免页面散落重复样式。

### 37.2 字号与字重

系统默认业务字号：13px。

建议：

- 普通正文/字段值/查询/文字按钮：400；
- 表头/页面标题/分区标题/应用名称/选中菜单：500；
- 顶部系统名称等少量一级标题：600；
- 强调数字按需 600。

### 37.3 页面标题与页面级操作

页面级主操作位于页面名称右侧。

例如：

- 新增公告；
- 新增应用；
- 下载接口文件；
- 新增角色。

不把页面级操作藏在列表卡片内部。

### 37.4 查询区

- 使用统一 inline 查询布局；
- 查询条件按语义设置合理宽度；
- 不强制所有字段等宽；
- 重置按钮不得被挤压或与条件重叠；
- 条件间距统一。

常用宽度参考：

| 类型 | 建议宽度 |
|---|---:|
| 关键词 | 220～360px |
| 状态 | 160～180px |
| 系统分类 | 220px |
| 用户类别 | 180～190px |
| 来源应用 | 260～280px |
| 日期区间 | 360px |

具体以页面内容不换行、不挤压为准。

### 37.5 列表与分页

- 表头、正文、分页以 13px 为基准；
- 主业务字段可作为详情入口；
- 详情入口使用蓝色普通字重；
- 操作列只保留真正的业务动作；
- 不重复放“详情”按钮；
- 列表白色内容区域不增加无意义外边框；
- 分页与列表间距统一。

### 37.6 Switch

全系统启停类状态统一命名“启用状态”。

使用 TDesign 默认无文字 Switch：

- 不在开关内部显示“启用/停用”；
- 不在开关旁重复显示相同文字；
- 列表、表单保持一致。

### 37.7 Dialog

- 默认垂直居中；
- 尺寸使用 TDesign 合理默认值或按内容适当加宽；
- 普通表单/确认 Dialog 的取消、保存、确认、提交放 Footer；
- 正文内容独立滚动；
- Footer 始终可见；
- 不因过度缩小造成字段拥挤；
- 避免 Dialog 内再次套无意义卡片；
- 详情信息间距保持统一。

### 37.8 Loading / Empty / Error

严格区分：

- Loading：正在读取；
- Empty：成功返回且真实为 0 条；
- Error：读取失败。

规则：

- 首次进入页面、切换页面时先 Loading；
- 数据准备完成前不渲染 Empty；
- 页面内保存/启停/审核后刷新可保留现有内容；
- 避免有数据页面先闪“暂无符合条件的记录”。

### 37.9 空值

全系统空值占位统一使用英文半角：

`-`

不得使用全角长横线 `—` 作为统一占位。

空值展示不代表数据库写入默认值。

### 37.10 折叠菜单

- 左侧菜单项文字统一使用 13px、字重500，避免普通菜单项与正文相比显得过细；选中项不再通过额外加粗制造跳变；
- 顶部系统名称旁的菜单折叠图标在不改变按钮占位的前提下增强视觉粗细，图标尺寸由16px调整为18px；
- 折叠后菜单图标提示使用 TDesign Tooltip，不使用浏览器原生 title 提示；
- 左侧菜单优先使用 TDesign 图标库；
- 不同业务页面尽量使用语义不同的图标，尤其同一端折叠后可见的菜单项不得大面积复用同一个默认图标；
- 首页、待办、申请、消息、公告、应用、用户、角色、组织、字典、映射、配置、监控和不同日志类型应尽可能形成可辨识的图标映射；
- 新增菜单时不得仅依赖“文件/文件夹”通用图标兜底，应明确配置图标。

### 37.11 卡片

- 普通信息卡减少阴影和大圆角；
- 应用卡片允许保留 1px 浅灰边框；
- Hover 可改浅蓝边框或轻微背景；
- 不通过强阴影制造层级；
- 用户侧不显示底层技术状态。

### 37.12 链接文字

- 全系统内容区普通可点击文字链接统一采用 13px、字重 400、品牌蓝 `#0052D9`；
- Hover 统一使用深蓝 `#003CAB` 并增加下划线，Hover 不改变字重；
- 用户端首页“我的待办 / 通知公告 / 消息”中的业务标题使用13px、字重500，并与“我的应用”中的系统名称字重一致；
- “全部待办 / 全部公告 / 全部消息 / 应用中心 / 查看全部”等页面跳转链接与列表页可点击字段采用普通蓝色链接规范；
- 应用卡片中的系统名称属于例外：虽然可点击进入详情，但首页“我的应用”和应用中心都统一使用黑色 `#1F2329`、13px、字重500，不使用蓝色链接视觉；
- 系统名称 Hover 继续保持黑色，不通过变蓝或加粗强调可点击性；
- 未读、重要、异常等状态不得通过把链接文字加粗来表达，应使用徽标、数量、Tag 或其他状态组件区分。

## 39. 数据隔离与安全

### 39.1 用户数据隔离

用户端：

- 待办只看本人；
- 消息只看本人；
- 公告按发布范围；
- 应用按用户类别、适用范围、入口资格和映射结果；
- 我的申请只看本人。

管理端根据角色权限访问管理数据。

### 39.2 凭据保护

不得记录：

- 外部身份密码；
- 子系统明文密码；
- OTP；
- Token；
- password_hash。

敏感连接凭据使用环境变量/凭据引用等方式管理。

### 39.3 后端鉴权

高风险写操作必须服务端二次鉴权，不能只依赖前端隐藏按钮。

### 39.4 审计

关键动作需记录：

- 操作人；
- 对象；
- 动作；
- 结果；
- 时间；
- 请求ID；
- 必要上下文。

## 45. 验收原则

### 45.1 身份与权限

- 三种身份来源识别正确；
- 用户类别与角色不混用；
- 无管理角色用户不能进入管理端；
- LOCAL 可独立登录；
- 默认角色仅超级管理员和门户管理员；
- 子系统业务权限不进入门户角色管理。

### 45.2 用户端

- 数据按当前用户隔离；
- 我的应用只显示已可使用应用；
- 其它应用显示结果和下一步，不暴露技术过程；
- 应用申请闭环；
- 账号异常/未开户/停用有明确结果；
- 待办、消息、公告正常展示；
- Loading 不闪 Empty。

### 45.3 管理端

- 应用、用户、角色、组织、字典、映射、配置可按权限管理；
- 应用连接配置入口唯一；
- 启用状态 Switch 统一；
- 身份映射详情分区和分页正确；
- 日志字段按类型展示；
- 异常日志可闭环；
- 运行监控只承担接入健康查看。

### 45.4 UI

- 默认 13px；
- Dialog 垂直居中；
- 页面级操作位于标题右侧；
- TDesign Tooltip；
- 无文字 Switch；
- 空值 `-`；
- Loading / Empty / Error 分离；
- 蓝色业务链接普通字重；
- 不出现重复无意义卡片和外层边框。

### 45.5 安全

- 明文密码不落库；
- password_hash 不返回前端；
- OTP/Token 不写日志；
- 高风险操作服务端鉴权；
- 映射冲突不得自动覆盖；
- 关键操作可追溯。

## 47. 文档维护约定

后续需求发生变化时：

1. 先确认最终业务口径；
2. 直接修改本文对应章节；
3. 同步必要的功能清单、设计文档和测试；
4. 不再创建长期并行的“V1.1 / V1.2 需求规格说明书”；
5. 文件名始终保持：
   `卫健统一门户系统需求规格说明书.md`；
6. 版本追溯交由 Git 提交历史完成；
7. 若需阶段冻结，在 Git Tag、Release 或交付清单中标识，不通过复制多份需求规格说明书实现。
