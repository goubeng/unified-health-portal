# 原始需求与当前实现差异及客户确认清单

> 对比基准：`docs/01-需求/01-原始需求/原始需求.md`  
> 当前业务基线：`docs/01-需求/02-当前基线/卫健统一门户系统需求规格说明书.md`（V20260921-01）  
> 当前实现范围：P4 / 0.3.0-A 高保真 Mock 原型，A3 冻结前收口。  
> 用途：用于与客户逐项确认原始建设要求与当前门户设计/实现之间的范围、职责和功能差异。  
> 注意：本文是“待确认差异清单”，不替代主需求规格说明书。客户确认后的结论应回写主需求规格说明书、功能清单和相关设计文档。

## 1. 总体判断

原始需求的范围明显大于当前“统一门户”原型。原始材料同时包含统一门户、统一登录、统一用户体系、角色权限、短信管理、数据汇聚治理、统一服务接口改造、微服务监控等内容；当前实现则已经收敛为：

- 闽政通/闽政务权威身份承接；
- 门户访问主体最小索引；
- 独立门户管理用户；
- 应用目录与应用入口资格；
- 子系统账号映射；
- SSO / TODO / MESSAGE 接入；
- 待办、消息、公告聚合；
- 门户角色权限；
- 组织、字典、配置、日志与接入健康管理。

因此，下列差异不能只视为“原型暂未完成”，需要客户确认哪些属于正式建设范围、哪些由上层平台/业务子系统/其他项目承担、哪些可以从本项目中删除。

## 2. 客户确认差异清单

| 序号 | 功能点 | 功能描述（原始需求、当前实现差异及需确认事项） |
|---|---|---|
| 1 | 纳管系统与整合后平台的展示关系 | 原始需求同时给出纳管系统及7个整合后平台，当前设计保留系统与整合后平台的归属关系。**需确认页面最终采用系统直接展示、按整合后平台分组展示，还是“整合后平台 + 下属系统”的二级目录。** |
| 2 | 门户首页与应用中心的应用呈现范围 | 原始需求描述“将各应用集成至平台工作门户上”，没有区分首页与应用中心。当前实现首页只展示“我的应用”，完整目录放在应用中心，并区分“我的应用/其它应用”。**需确认客户是否要求首页直接展示全部可见应用，还是认可当前首页聚合 + 应用中心完整目录的方式。** |
| 3 | 统一用户主数据归属 | 原始需求描述平台基础库包含用户信息，并对用户进行统一管理；当前设计明确门户不建设公众/政务完整用户主库，只保存CITIZEN/GOV最小访问索引，权威身份归闽政通/闽政务。**需确认门户是否只承接上层身份，还是仍要求维护一套完整用户主数据。** |
| 4 | 自然人、法人、企业用户范围 | 原始需求提到统一身份认证服务为自然人、法人及企业用户提供注册、登录和核验。当前用户端只建模公众用户CITIZEN和政务用户GOV，没有单独的法人/企业用户类型。**需确认法人、企业用户是否属于本门户首期用户对象；如属于，需要明确身份来源、登录方式、应用范围和组织关系。** |
| 5 | 用户注册职责 | 原始需求要求各应用注册、登录调用省一体化平台；当前门户不自行完成公众/政务注册，相关入口跳转或承接上层能力。**需确认客户是否认可“注册完全由上层身份平台负责”，门户只做入口和结果承接。** |
| 6 | 用户新增功能 | 原始需求要求可按机构区域新增用户，并录入用户名、账号、密码、有效状态、用户类型。当前“用户管理”只管理门户管理用户；普通公众/政务用户不在门户新增。本地新增仅用于管理账号。**需确认原始“用户新增”是否仍是门户正式功能，还是应由闽政通/闽政务负责。** |
| 7 | 用户信息修改功能 | 原始需求允许修改用户名称、机构、有效状态、用户权限等级等。当前外部身份型用户的姓名、手机号、账号、身份来源等权威字段只读，门户只维护管理资格、门户角色和启用状态。**需确认门户可修改哪些字段，避免与上层主数据产生双主。** |
| 8 | 用户作废/停用 | 原始需求要求“一键设置用户无效”。当前实现区分“门户访问主体状态”和“门户管理用户启用状态”，停用管理资格不会停用其闽政通/闽政务账号。**需确认所谓“用户作废”是只禁止访问门户、禁止进入管理端，还是需要联动上层身份账号。** |
| 9 | 用户必须隶属组织 | 原始需求明确“每个用户都隶属于某个组织机构”。当前设计政务用户可有组织，公众用户CITIZEN不强制组织。**需确认公众用户是否也必须挂组织；如果必须，需要明确公众用户组织来源和无组织用户处理方式。** |
| 10 | 用户等级模型 | 原始需求列出超级用户、普通用户、系统管理员、行政管理员等“用户等级”。当前模型拆成“用户类别（CITIZEN/GOV）+ 门户角色（SUPER_ADMIN/PORTAL_ADMIN/自定义）”，不再使用单一用户等级。**需确认是否接受当前拆分，还是客户仍要求保留用户等级字段及等级规则。** |
| 11 | 门户本地管理账号 | 原始需求未明确单独的门户本地管理账号体系；当前为了初始化、运维和无上层身份的管理员场景，增加PORTAL_LOCAL本地管理账号。**需确认是否允许正式环境保留本地管理账号，以及账号数量、密码策略、二次认证和交付初始化方式。** |
| 12 | 用户组管理 | 原始角色管理中包含“用户组/用户的创建、编辑、删除”。当前没有独立用户组模块，角色直接分配给门户管理用户。**需确认是否必须建设用户组；若需要，应明确用户组与组织、角色、应用授权之间的关系。** |
| 13 | 角色预置范围 | 原始需求示例中存在超级用户、系统管理员、行政管理员等多类管理角色；当前首期只预置“门户超级管理员、门户管理员”，其它按需自定义。**需确认客户是否要求预置更多固定角色，例如应用管理员、公告管理员、审计管理员、集成管理员等。** |
| 14 | 角色删除 | 原始需求明确角色支持创建、编辑、删除；当前角色页支持新增、编辑/权限配置、启停，但未开放删除。**需确认自定义角色是否必须支持物理删除/逻辑删除，以及已有用户关联时的删除规则。** |
| 15 | 权限管理独立模块 | 原始需求把“角色管理”和“权限管理”分别描述；当前把权限配置并入角色管理，通过“菜单→页面→操作”配置，不再设置独立权限管理菜单。**需确认客户是否接受合并，还是必须保留独立“权限管理”模块。** |
| 16 | 应用访问授权模型 | 原始需求强调“采用角色授权，只有被授权指定系统的角色用户才能访问”；当前应用入口采用DIRECT/BIND/REQUEST，REQUEST按用户申请/审核产生入口资格，并不以门户角色直接授权业务应用。**这是核心差异，需要确认应用访问最终是“角色→应用授权”、 “用户申请/授权”，还是两者并存。** |
| 17 | 门户角色是否管理子系统业务权限 | 原始材料容易理解为统一角色权限中心；当前明确门户角色只管理门户自身菜单/页面/操作，不创建、修改或分配子系统业务角色、菜单和数据权限。**需客户明确确认子系统内部业务授权是否完全由各子系统自行负责。** |
| 18 | 平台统一分配子系统账号 | 原始“业务协同关系分析”描述平台统一分配帐号，用户登录后可单点登录有权限的垂直系统。当前门户不直接创建/分配子系统账号，只做账号映射、确认和状态承接。**需确认是否仍存在“门户统一开户/统一分配账号”的硬性要求；如有，当前边界需要重大调整。** |
| 19 | 身份与子系统账号映射 | 当前新增“身份与子系统映射”，支持候选匹配、二次验证、审核、冲突、解绑等，原始需求没有明确这一独立模块。该能力用于解决历史子系统已有账号与统一身份之间的对应关系。**需确认是否认可该新增能力及其审核/解绑职责由门户承担。** |
| 20 | 子系统账号开通申请 | 当前允许在子系统提供标准接口时，由门户发起或承接账号开通申请状态，但门户不直接开户注册。原始需求更多倾向平台统一分配帐号。**需确认各子系统是“门户代办申请、子系统开户注册”，还是“门户直接创建账号”，以及哪些系统支持标准开户接口。** |
| 21 | 系统分类管理位置 | 原始需求有独立“分类管理”模块；当前将系统分类并入“字典管理”，应用列表引用分类字典，不再保留单独菜单。**需确认客户是否接受合并；如验收清单明确要求独立分类管理页面，需要恢复。** |
| 22 | 接入密钥管理 | 原始接入管理要求维护系统名称、接入代码、系统地址、秘钥、系统分类等。当前连接配置保留Client ID、服务地址、协议等，但真实Secret/Token/私钥只允许保存安全凭据引用，不在前端明文展示。**需确认正式凭据由哪个密钥服务/配置中心保管，门户是否需要提供凭据录入能力。** |
| 23 | 待办定期催办提醒 | 原始需求明确“若接收者没有及时处理，则会定期收到消息提醒”。当前待办只聚合PENDING/COMPLETED/WITHDRAWN，不同步截止时间、不判断逾期，也没有定时催办任务。**需客户确认是否必须建设催办；若需要，应明确由门户还是来源系统触发、提醒周期、停止条件、提醒渠道及是否需要截止时间。** |
| 24 | 消息自动产生规则 | 原始需求描述系统根据登录用户“自动发送相关消息提醒到工作台”。当前消息主要由业务子系统通过MESSAGE PUSH进入门户，另有门户自身业务消息，不建设通用消息规则引擎。**需确认消息到底由各子系统产生并推送，还是门户需要根据业务规则主动生成消息。** |
| 25 | 公告固定格式/模板 | 原始需求要求通知公告“按照固定格式和自定义发布”。当前支持富文本、自定义正文、附件、立即/定时发布等，但没有“固定公告模板/模板库”管理。**需确认“固定格式”是否指固定页面版式即可，还是需要可维护的公告模板、套红/格式模板等功能。** |
| 26 | 公告发布范围 | 当前公告范围主要为全部、公众、政务，组织级发布仅作为后续扩展。原始需求只写“统一下发”，未明确范围。**需确认是否需要按组织、部门、角色、指定人员或应用进行定向公告。** |
| 27 | 短信管理总体范围 | 原始需求明确建设独立短信管理，包括渠道、内容、模板、定时发送、记录、失败重发、费用统计。当前SRS明确首期不建设门户自有短信管理，登录验证码优先由闽政通/闽政务或统一短信服务提供，子系统OTP优先由子系统提供。**需客户确认短信能力究竟由谁建设和运营，是上层公共能力、门户代理，还是各业务系统自行发送。** |
| 28 | 短信模板与定时发送 | 原始需求要求预置筛查提醒、复检通知、结果异常告知等模板，支持自定义内容和发送时间。当前没有短信模板库和短信定时任务。**如果短信仍属于本项目，需要确认模板审批、变量、适用业务、定时机制和隐私脱敏要求。** |
| 29 | 短信发送记录与失败重发 | 原始需求要求查询发送记录、失败重发。当前没有短信发送记录和重试队列。**如由上层短信平台提供，应明确门户只查询结果还是完全不参与；如门户代理，则需新增发送状态、错误码、重试次数、补发权限和审计。** |
| 30 | 短信费用统计 | 原始需求明确“费用统计”。当前明确不建设。**需重点确认短信通道由谁付费、是否能获取运营商/服务商计费明细、计费粒度是短信条数还是模板/部门/应用、是否存在套餐/阶梯价格。若短信由上层统一服务提供且门户拿不到可靠费用数据，建议不在门户重复建设费用统计。** |
| 31 | 配置管理—业务/性能阈值 | 原始需求要求配置应用版本状态、业务状态、性能状态等临界值及异常告警阈值。当前配置管理主要维护门户级业务规则，运行监控也只做SSO/TODO/MESSAGE接入健康。**需确认是否要求门户维护性能/业务告警阈值；如果要求，需要明确指标来源和监控责任。** |
| 32 | 配置管理—角色个性化界面 | 原始需求要求“配置系统各种角色的个性化界面”。当前权限只控制菜单/页面/操作，不提供按角色配置主题、布局、首页组件等个性化界面。**需确认此项是否仍保留，以及“个性化界面”具体指菜单权限还是界面布局/主题。** |
| 33 | 日志类型与范围 | 原始需求主要要求登录、登出、登入子系统，并可记录认证、权限检测和操作日志。当前实现拆为登录/认证、应用访问、门户操作、接口调用、异常五类日志。**需确认是否要求单独记录“登出日志”和“权限检测日志”，以及当前五类日志是否可覆盖验收。** |
| 34 | 日志策略可配置 | 原始需求提出管理员可根据资源可靠性/机密性配置是否记录认证、权限检测、操作日志。当前日志类型和关键操作审计规则是固定设计，没有“日志策略配置”页面。**需确认是否必须支持按资源配置日志级别/类型。** |
| 35 | 统一数据采集汇聚 | 原始需求包含省卫健委业务数据推送至医疗数据专区、数据集成、专项库建设等。当前统一门户完全不承担业务数据采集汇聚，只聚合门户访问所需的应用、待办、消息、账号映射等轻量数据。**需确认数据汇聚治理是否属于另一个平台/标段；若属于本项目，当前范围明显不足。** |
| 36 | 数据治理与“三医一张网”规范 | 原始需求要求按相关数据治理规范完成门诊、住院、病案、病历、医疗管理等数据整合。当前门户没有专项库、数据质量、标准映射、治理任务。**需确认该部分是否从统一门户剥离；若不剥离，应单独立项/模块设计，不能按门户页面功能简单补齐。** |
| 37 | 统一服务接口改造范围 | 原始需求提出统一预约、检验结果互认、健康档案等对外服务依托省一体化微服务能力建设。当前门户只设计SSO/TODO/MESSAGE三类统一接入，不建设通用业务服务目录/API网关。**需确认本项目是否需要承担更广泛的业务服务接口改造。** |
| 38 | 微服务治理/APM能力 | 原始需求要求全面监控、分布式调用链分析和日志分析。当前“运行监控”只查看每个应用SSO/TODO/MESSAGE的未配置/停用/正常/异常，不建设主机监控、调用链、APM。**需确认这些能力由省一体化支撑平台提供，还是本门户也要建设；如上层已有，建议门户只展示必要健康摘要。** |
| 39 | 网络区域与访问策略 | 原始应用清单明确标注政务外网、互联网、卫健专网、公用网络区等网络情况。当前Mock保留networkZone信息，但尚未把网络区域用于可见性、路由、网络提示或接入策略。**需确认不同网络区是否会影响用户可访问范围、入口跳转、VPN/专线要求或管理端配置。** |
| 40 | 第三方系统用户/角色数据采集 | 原始数据架构把第三方系统用户信息、角色信息和系统基础信息列为外部数据。当前门户只维护应用目录和必要账号映射，不批量同步各子系统角色。**需确认是否要求定期采集子系统用户/角色数据；若要求，应明确用途、同步频率和主数据冲突处理。** |
| 41 | 应用访问申请功能 | 当前增加“我的申请/应用访问申请审核”，用于REQUEST模式下获取门户入口资格；原始需求没有独立申请流程，而是强调角色授权。**需客户确认是否认可新增申请审批流程，以及哪些系统需要申请、谁审核、是否需要授权有效期。** |
| 42 | 应用授权有效期 | 当前模型预留申请EXPIRED状态，但应用入口授权是否有有效期尚未正式确定。原始需求也未明确。**需确认审批通过后是永久有效、按日期有效，还是随岗位/组织/角色变化自动失效。** |
| 43 | 子系统账号解绑/重绑 | 当前身份映射支持管理员解绑和冲突处理，是否允许用户自助解绑仍待确认。原始需求未描述。**需确认普通账号与高权限账号的解绑、重绑权限和审批要求。** |
| 44 | 应用接入协议与逐系统摸底 | 当前支持OIDC/SAML2/CAS/Token/自定义等目标协议并要求逐系统摸底；原始需求只强调单点登录。**需客户提供每个系统真实登录方式、稳定用户ID、账号查询接口、回调和网络条件，才能确定最终接入工作量。** |
| 45 | 正式数据持久化范围 | 当前原型默认MEMORY_A，数据库生产化不作为P4演示验收门槛；原始需求显然面向正式建设。**需客户确认下一阶段是否立即进入正式数据库CRUD/迁移，还是先冻结原型并以原型作为需求确认成果。** |
| 46 | 原型与正式系统边界 | 当前实现是高保真Mock原型，真实闽政通/闽政务、42个有效原系统逐一联调尚未完成。**需与客户明确原型验收只能确认页面、流程和接口契约，不应被理解为已经完成生产接入。** |

## 3. 建议优先确认顺序

建议客户会议优先确认以下高影响问题，确认结果会直接改变系统边界、数据模型或后续工作量：

1. 纳管系统与7个整合后平台的展示关系：确认是直接展示、按平台分组，还是采用“平台 + 下属系统”二级目录。
2. 用户体系：门户是否自建完整用户库，公众/政务是否允许门户新增/修改，法人/企业是否纳入。
3. 权限体系：应用访问究竟采用“角色授权”还是“用户申请/账号映射”，子系统业务权限是否完全下放子系统。
4. 子系统账号：门户是否负责统一开户注册，还是只做映射与申请状态承接。
5. 短信：是否属于本项目；若属于，渠道、模板、重发、费用统计由谁提供数据。
6. 待办催办：是否必须由门户做定期提醒，还是来源系统负责。
7. 公告固定格式：是否需要真正的模板管理和更细发布范围。
8. 数据汇聚治理：是否属于本门户；若属于，需要单独的数据平台工作包。
9. 微服务/API治理/APM：是否由省一体化支撑平台提供，门户只展示健康摘要。
10. 网络区域：不同网络区是否影响门户入口、用户可见性及接入方式。

## 4. 客户确认后的文档处理规则

- 客户确认“保留/新增”的功能：回写主《需求规格说明书》、功能清单、页面/字段/流程设计，并评估数据库与接口影响；
- 客户确认“由上层平台负责”的功能：在SRS责任边界中明确上层责任和门户仅承接内容；
- 客户确认“由业务子系统负责”的功能：明确门户只做入口、映射、状态或跳转，不重复建设；
- 客户确认“不建设”的功能：在SRS“首期不纳入范围”中明确，避免验收时再次按原始需求追责；
- 影响数据库、接口、角色或状态机的确认项，必须同步数据设计、Service契约、Migration计划和测试基线。
