# 原始需求与当前实现差异及客户确认清单

> **对比依据**：原始需求文档、当前《卫健统一门户系统需求规格说明书》及相关细化需求。  
> **用途**：用于逐项确认原始需求与当前设计之间的功能范围、责任边界及实现口径。  
> **确认结果**：由客户在确认后填写，可填写“按当前设计执行 / 调整需求 / 上层平台负责 / 业务子系统负责 / 其他平台或项目负责 / 本期不建设 / 待进一步确认”等结论。

> 2026-10-01 阅读边界：文件名沿用历史命名，表格实际比较的是“原始需求与当前目标设计”，并非逐项代码实现验收；空白客户确认栏仍待正式确认。现行代码实现与测试缺口另见开发评审的代码与文档一致性核查。

## 1. 当前设计总体边界

当前统一门户按以下总体边界进行设计：

- **上层身份平台**：闽政通负责公众权威身份，闽政务负责政务权威身份；正式开户注册、实名核验、验证码及外部账号安全原则上由上层身份能力提供。
- **统一门户**：负责统一登录入口、Portal Session、最小用户索引、门户管理用户与门户角色、应用目录与入口资格、必要的子系统账号映射、待办/消息聚合、公告、组织/字典/配置、日志以及 SSO / TODO / MESSAGE 接入健康。
- **业务子系统**：负责子系统账号本体、开户注册、账号启停、业务角色、菜单权限、数据权限、业务审批及账号真实性。
- **应用访问**：门户负责“能否从门户看到、申请、进入某个应用”；进入子系统后的业务权限由子系统自行判定。
- **纳管范围**：纳管系统数量为 **42 项**；同时保留与 7 个整合后平台的归属关系。
- **运行监控**：定位为应用接入健康查看，不等同于完整 APM、主机监控或分布式调用链平台。
- **短信能力**：是否由门户建设完整短信运营能力仍需结合上层统一短信能力及责任归属确认。
- **数据范围**：门户以统一访问、应用接入和公共事务聚合所需数据为主，不默认承担业务数据中心或医疗业务数据汇聚职责。

## 2. 影响级别说明

- **高影响**：确认结果会改变系统建设边界、核心数据模型、权限模型、外部接口、账号体系、42 项系统接入方式或形成明显新增工作量。
- **中影响**：主要影响页面结构、业务流程、配置规则、日志策略、运营方式或局部后端实现，一般不改变系统总体架构。

| 8 | 用户作废/停用 | 原始需求要求“一键设置用户无效”。当前设计区分“门户访问主体状态”和“门户管理用户启用状态”，停用管理资格不会停用其闽政通/闽政务账号。需确认所谓“用户作废”是只禁止访问门户、禁止进入管理端，还是需要联动上层身份账号。 | 门户仅控制门户访问资格和管理端启用状态，不直接改变闽政通/闽政务账号状态。 | 账号状态模型、登录鉴权、上层身份联动、审计 | **高影响** |  |
| 9 | 用户必须隶属组织 | 原始需求明确“每个用户都隶属于某个组织机构”。当前设计政务用户可有组织，公众用户CITIZEN不强制组织。需确认公众用户是否也必须挂组织；如果必须，需要明确公众用户组织来源和无组织用户处理方式。 | 政务用户可引用上层组织；公众用户不强制组织。组织首期主要用于资料、检索和后续公告范围。 | 用户模型、组织同步、查询、公告范围、权限扩展 | **中影响** |  |
| 10 | 用户等级模型 | 原始需求列出超级用户、普通用户、系统管理员、行政管理员等“用户等级”。当前模型拆成“用户类别（CITIZEN/GOV）+ 门户角色（SUPER_ADMIN/PORTAL_ADMIN/自定义）”，不再使用单一用户等级。需确认是否接受当前拆分，还是客户仍要求保留用户等级字段及等级规则。 | 用户类别与门户角色分离；管理权限由门户管理用户、角色和权限共同决定，不以单一“用户等级”字段表达。 | 身份模型、角色权限模型、数据库、鉴权逻辑 | **高影响** |  |
| 11 | 门户本地管理账号 | 原始需求未明确单独的门户本地管理账号体系；当前为了初始化、运维和无上层身份的管理员场景，增加PORTAL_LOCAL本地管理账号。需确认是否允许正式环境保留本地管理账号，以及账号数量、密码策略、二次认证和交付初始化方式。 | 本地账号仅用于管理端认证，不形成第三类普通用户；必须分配门户角色，并遵守独立凭证与安全策略。 | 管理端登录、账号安全、凭证存储、初始化与运维 | **高影响** |  |

| 18 | 平台统一分配子系统账号 | 原始“业务协同关系分析”描述平台统一分配帐号，用户登录后可单点登录有权限的垂直系统。当前门户不直接创建/分配子系统账号，只做账号映射、确认和状态承接。需确认是否仍存在“门户统一开户/统一分配账号”的硬性要求；如有，当前边界需要重大调整。 | 子系统账号本体、开户注册、启停和高权限账号管理归业务子系统；门户不直接创建业务账号。 | 账号体系、子系统接口、开户流程、数据库、安全、接入工作量 | **高影响** |  |
| 19 | 身份与子系统账号映射 | 原始需求提出统一管理接入系统用户信息、平台账号及单点登录，但未明确独立的“身份与子系统账号映射”模块。当前方案在明确“子系统账号及业务权限由各子系统负责、门户不直接创建子系统账号”的边界后，为解决统一身份与各历史子系统已有账号之间的对应关系，增加身份与子系统账号映射能力，包括账号发现、身份确认、审核、冲突处理及解绑等。需确认该账号映射能力是否由统一门户承担，以及门户需要管理到什么深度。 | 账号映射对象为“门户访问主体 ↔ 子系统账号”；门户负责必要的映射管理，但子系统账号真实性及业务权限仍归子系统。 | 账号映射模型、BIND流程、账号校验接口、审核、冲突、解绑、SSO | **高影响** |  |
| 20 | 子系统账号开通申请 | 当前允许在子系统提供标准接口时，由门户发起或承接账号开通申请状态，但门户不直接开户注册。原始需求更多倾向平台统一分配帐号。需确认各子系统是“门户代办申请、子系统开户注册”，还是“门户直接创建账号”，以及哪些系统支持标准开户接口。 | 仅在子系统提供标准开户注册能力时由门户发起或承接申请状态；实际账号创建仍由子系统完成。 | 账号开通流程、子系统接口、申请状态、页面与审计 | **高影响** |  |
| 21 | 系统分类管理位置 | 原始需求有独立“分类管理”模块；当前将系统分类并入“字典管理”，应用列表引用分类字典，不再保留单独菜单。需确认客户是否接受合并；如验收清单明确要求独立分类管理页面，需要恢复。 | 系统分类作为业务字典维护，应用列表引用分类字典，不设置独立“分类管理”菜单。 | 菜单结构、字典管理、应用管理、验收口径 | **中影响** |  |
| 22 | 接入密钥管理 | 原始接入管理要求维护系统名称、接入代码、系统地址、秘钥、系统分类等。当前连接配置保留Client ID、服务地址、协议等，但真实Secret/Token/私钥只允许保存安全凭据引用，不在前端明文展示。需确认正式凭据由哪个密钥服务/配置中心保管，门户是否需要提供凭据录入能力。 | 真实Secret、Token、私钥不得在前端、普通API或代码仓库中明文保存；当前仅定义安全引用方式。 | 安全架构、密钥服务/配置中心、连接配置、部署运维 | **高影响** |  |
| 23 | 待办定期催办提醒 | 原始需求明确“若接收者没有及时处理，则会定期收到消息提醒”。当前待办只聚合PENDING/COMPLETED/WITHDRAWN，不同步截止时间、不判断逾期，也没有定时催办任务。需客户确认是否必须建设催办；若需要，应明确由门户还是来源系统触发、提醒周期、停止条件、提醒渠道及是否需要截止时间。 | 待办仅聚合PENDING/COMPLETED/WITHDRAWN，不同步优先级、截止时间或逾期，不由门户自行生成催办。 | 待办模型、定时任务、消息规则、子系统字段、提醒渠道 | **高影响** |  |

## 4. 重点确认事项

以下事项建议优先确认，因为其结论会直接影响后续系统边界或整体实施工作量：

1. **用户体系与身份边界**：统一用户主数据归属、法人/企业用户范围、用户新增/修改/作废、本地管理账号。
2. **权限与应用访问模型**：用户等级、用户组、门户角色与子系统权限边界、应用访问采用角色授权还是 DIRECT / BIND / REQUEST。
3. **子系统账号体系**：是否由门户统一分配账号、身份与子系统账号映射深度、账号开通申请、解绑/重绑规则。
4. **42 项系统接入方式**：SSO 协议、稳定用户标识、账号查询/校验接口、网络区域以及 TODO / MESSAGE 接入能力。
5. **待办与消息责任边界**：门户是否承担定期催办和通用消息规则引擎。
6. **短信建设范围**：短信渠道、模板、发送记录、失败重发、费用统计以及责任归属。
7. **数据与平台能力边界**：业务数据采集汇聚、通用业务服务接口、微服务治理 / APM 是否属于统一门户建设范围。
