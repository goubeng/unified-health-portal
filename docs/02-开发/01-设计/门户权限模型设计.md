# 门户权限模型设计

> 目标：定义谁能进入管理端、进入后能做什么。门户权限不管理 42 个子系统内部业务权限。

## 1. 身份与授权分离

认证回答“你是谁”，授权回答“你是否可以管理门户”。

外部身份可来自：
- MINZHENGTONG；
- MINZHENGWU。

管理端授权主体为 `portal_admin_user`。一个门户管理用户可以：
- 绑定一个门户访问主体/外部身份；
- 或使用门户本地账号认证。

外部用户认证成功但未建立有效 `portal_admin_user` 授权时，不得进入管理端。

## 2. RBAC

```text
PORTAL_ADMIN_USER
  → ADMIN_USER_ROLE
  → PORTAL_ROLE
  → ROLE_PERMISSION
  → PORTAL_PERMISSION
```

默认只预置：
- SUPER_ADMIN：门户超级管理员；
- PORTAL_ADMIN：门户管理员。

未来允许创建自定义角色，但不把“应用管理员/公告管理员/审计管理员”等固定为用户类型。

## 3. 权限编码

第一阶段按“资源:操作”控制：

- dashboard:view
- admin-user:view/create/edit/enable/delete/assign-role
- role:view/create/edit/enable/delete/permission-config
- application:view/create/edit/enable/delete
- integration:view/edit/enable/test
- monitor:view/check
- mapping:view/retry/unbind
- announcement:view/create/edit/publish/withdraw/delete
- audit:view

页面菜单不是安全边界。前端隐藏按钮后，后端仍必须校验权限。

## 4. 多角色规则

一个门户管理用户可拥有多个角色，权限取并集。第一阶段不引入显式 DENY；未授权即拒绝。

## 5. 最后一个超级管理员保护

“有效超级管理员”定义为：
- 门户管理用户启用；
- SUPER_ADMIN 角色启用；
- 用户拥有 SUPER_ADMIN。

任何停用、删除、移除角色、停用角色的操作，只要会导致有效超级管理员数量为 0，后端必须拒绝并返回 `LAST_SUPER_ADMIN_PROTECTED`。

## 6. 管理端进入流程

```text
认证成功
→ 定位 portal_admin_user
→ 检查 enabled
→ 加载角色
→ 加载权限
→ 允许进入管理端
```

本地账号也必须经过相同的角色/权限计算，不因“本地账号”自动获得管理员权限。

## 7. 子系统权限隔离

门户角色不得：
- 创建/修改子系统业务角色；
- 分配子系统菜单；
- 分配子系统数据权限；
- 代替子系统业务审批。

门户超级管理员也不自动拥有任一子系统业务权限。

## 8. 前端权限守卫

前端登录态至少缓存：
- adminAccess；
- adminUser；
- roles；
- permissions。

用途：
- 菜单显示；
- 路由守卫；
- 按钮显示。

最终授权结果仍以后端为准。
