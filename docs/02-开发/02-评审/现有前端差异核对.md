# 现有前端差异核对（V20260921-01）

> 核对范围：当前 main 分支 Vue/Vite 前端、Mock Service、本地 API 与已确认的后端详细设计。  
> 结论：现有页面布局与主要交互可以继续使用，不需要推翻重做；主要差异集中在数据主体、API 契约、状态语义和权限控制。

## 1. 总体结论

| 范围 | 结论 |
|---|---|
| 登录页视觉/布局 | 保留 |
| 用户端菜单结构 | 保留 |
| 管理端菜单结构 | 基本保留 |
| 应用中心交互 | 基本保留，替换真实能力判断 |
| 管理端用户管理 | 中等调整，对象改为 portal_admin_user |
| 角色管理 | 小～中调整，粗粒度 scope 改正式 permission |
| 应用列表/详情 | 小调整，综合运行状态改派生 |
| 连接配置 | 基本保留，字段命名与数据源调整 |
| 运行监控 | 基本保留，真实检测替换 Mock |
| 身份与子系统映射 | 保留，只面向访问主体 |
| 待办 | 小调整，去 EXPIRED/sourceRevision 等旧契约 |
| 消息 | 小调整，删除改用户级逻辑删除 |
| 公告 | 小～中调整，展示状态与持久化状态分离 |
| 日志 | 小调整，actor 区分访问主体/管理用户 |
| 通用请求层 | 需要重构，从 read/command 切到目标 REST API |

## 2. FE-01 当前用户模型仍混在 state.users

当前：
- `src/mock/seed.js` 把普通用户、外部管理员和 LOCAL 管理员都放入 actors/users；
- `src/services/portal.js` 的用户管理、角色统计、Session 都围绕同一个 `d.users`；
- `createLocalPortalUser` 仍创建 `userType:'LOCAL'` 用户。

目标：
- accessUsers / unified_user：仅 CITIZEN/GOV；
- adminUsers / portal_admin_user：独立管理授权主体；
- LOCAL 只存在于 portal_admin_user + credential。

影响：P0。管理端用户管理与 Session 数据层必须调整。

## 3. FE-02 用户管理页面字段仍按普通用户设计

当前 `PortalPage.vue`：
- users 查询仍基于 CITIZEN/GOV userType；
- 列表主要字段是 name/account/orgName/userType/roleLabels/status；
- 编辑动作仍叫 `savePortalUser`。

目标：
- 管理账号；
- 姓名；
- 认证类型 EXTERNAL/LOCAL；
- 身份来源；
- 门户角色；
- 启用状态；
- 最近管理端登录。

EXTERNAL 可在详情显示绑定用户类别，但不再把 CITIZEN/GOV 当作管理用户自身类别。

影响：P0，中等页面调整。

## 4. FE-03 权限仍为粗粒度 scopes

当前：
- super
- system
- application
- integration
- announcement
- audit
- identity

目标：
- application:view
- application:edit
- admin-user:assign-role
- announcement:publish
- integration:test
- monitor:check
- 等资源+操作权限。

`router.js` 的 `can(actor, scope)` 可以保留过渡兼容层，但正式阶段需要同时控制菜单、路由、按钮，并由后端再次鉴权。

影响：P0，权限适配层调整，不需要修改菜单视觉。

## 5. FE-04 API 调用模式与目标契约不同

当前：
- `GET /api/portal/read?resource=...`
- `POST /api/portal/command`

目标：
- `/api/auth/*`
- `/api/portal/*`
- `/api/apps/*`
- `/api/todos/*`
- `/api/messages/*`
- `/api/admin/*`
- `/api/integration/v1/*`

建议新增领域 Service：
- authApi；
- portalApi；
- appApi；
- todoApi；
- messageApi；
- announcementApi；
- adminUserApi；
- roleApi；
- integrationApi；
- auditApi。

影响：P0，但应优先在 Service/Data Adapter 层完成，避免页面逐个直接 fetch。

## 6. FE-05 应用仍使用单一 runtimeStatus

当前应用列表可以按 `app.runtimeStatus` 查询，`enterApp/openTodo` 也直接检查应用综合运行状态。

目标：
- APPLICATION 只保存启用状态；
- SSO/TODO/MESSAGE 各自保存运行状态；
- “进入/去处理”主要关注 SSO 及入口资格；
- 应用列表如果继续显示“运行状态”，由后端返回派生的 aggregateRuntimeStatus。

影响：P0，小调整，现有运行状态展示可以保留。

## 7. FE-06 接入配置已经较接近目标

当前已经按应用生成 SSO/TODO/MESSAGE 三类 integration，这是可直接复用的成果。

需要统一：
- `configurationStatus` → `configStatus`；
- `connectionStatus/status` → `runtimeStatus`；
- `enabled` 保持独立；
- 测试连接只能触发检测，不能由前端直接把状态改成 NORMAL。

影响：P0，小调整。

## 8. FE-07 TODO 仍残留旧字段/状态

当前：
- 查询条件仍包含 EXPIRED；
- Mock 录入表单仍要求 sourceRevision；
- 部分枚举仍保留 EXPIRED。

目标：
- PENDING / COMPLETED / WITHDRAWN；
- 不展示 priority/dueAt/逾期；
- 不依赖 sourceRevision；
- “去处理”不改变业务状态。

影响：P0，小调整。

## 9. FE-08 消息删除目前是物理移出当前数组

当前 `deleteMessages`：
- 复制到 messageTrash；
- 从 `d.messages` 中删除。

目标：
- message 本体保留；
- 当前用户 `message_recipient.deleted=true`；
- 多接收人之间互不影响。

影响：P0，Service/数据结构调整；页面操作方式不需要改变。

## 10. FE-09 公告页面状态与数据库目标不同

当前前端/Mock使用：
- DRAFT；
- SCHEDULED；
- PUBLISHED；
- WITHDRAWN；
- EXPIRED。

目标数据库：
- DRAFT；
- PUBLISHED；
- WITHDRAWN。

页面仍可以显示：
- SCHEDULED；
- EXPIRED。

建议正式 API 返回：
- `status`：持久化主状态；
- `displayStatus`：DRAFT/SCHEDULED/PUBLISHED/WITHDRAWN/EXPIRED。

这样现有公告交互可最大限度保留。

## 11. FE-10 当前登录仍是本地“选用户”

`runtime.js` 当前通过 `session({userId})` 切换 Mock 用户。

目标：
- 用户端闽政通/闽政务认证；
- 外部身份管理员认证后加载 adminAccess；
- LOCAL 使用独立管理账号密码；
- `GET /api/auth/me` 返回 accessSubject/adminUser/roles/permissions。

登录页视觉、二维码区、公众/政务切换可以保留，主要替换底层 Provider。

影响：主要在 0.3.0-C，但接口适配属于 P0。

## 12. FE-11 Router 仅做前端粗权限保护

当前：
- 无 actor → /login；
- scope 不匹配 → /portal/home。

目标：
- 用户端登录状态；
- adminAccess；
- page permission；
- 403 无权限反馈；
- 后端同步鉴权。

影响：P1 体验调整；安全边界必须由后端 P0 保证。

## 13. FE-12 管理首页“门户用户”口径有歧义

当前统计把 `d.users` 作为一个整体。

建议：
- “门户访问用户” = unified_user 数量；
- “门户管理用户” = portal_admin_user 数量（如需要可单列）。

如果首页只保留一个用户指标，建议使用“门户访问用户”，避免与管理端“用户管理”对象混淆。

## 14. FE-13 日志主体需要拆分

当前审计 actor 主要使用同一个 userId/userType。

目标区分：
- ACCESS_USER；
- PORTAL_ADMIN_USER；
- APPLICATION；
- SYSTEM。

页面仍可显示“操作人/来源应用”，但详情与 API 数据结构需要调整。

## 15. FE-14 外部 PUSH 契约仍是原型路径与 Bearer

当前：
- `/api/portal/ingest/{appId}/todos`
- `/api/portal/ingest/{appId}/messages`
- Bearer env credential。

目标：
- `/api/integration/v1/todos`
- `/api/integration/v1/todos/status`
- `/api/integration/v1/messages`
- AppKey + Timestamp + Nonce + Signature。

管理页面影响较小，但“下载接口文件”的 OpenAPI 内容需要同步。

## 16. 可以直接保留的前端成果

以下不因本轮详细设计推翻：
- Vue + Vite + TDesign；
- 当前菜单层级与折叠方式；
- 登录页视觉和背景；
- 页面标题、查询、列表、详情整体布局；
- 弹窗/右侧详情交互；
- 应用中心“我的应用/其它应用”；
- 待办详情和消息详情展示方式；
- SSO/TODO/MESSAGE 三列运行监控；
- 公告富文本、附件、预览和发布方式交互；
- 当前已确认的原型 UI 细节规则。

## 17. 推荐前端改造顺序

1. 建立新的 API Client 与统一错误处理；
2. Session 返回模型拆成 accessSubject/adminUser；
3. 用户管理切换到 adminUser；
4. permissions 替换 scopes；
5. integration 字段统一；
6. TODO 状态/字段清理；
7. message recipient 逻辑删除模型；
8. announcement status/displayStatus 适配；
9. app aggregateRuntimeStatus 适配；
10. 外部真实认证和 SSO 联调。

原则：先改 Service/Data Adapter，再改页面字段，避免页面直接绑定数据库物理结构。

## 18. 是否需要立即重做前端

结论：不需要。

0.3.0-B Schema/API 稳定前不建议大面积重做视觉页面。当前可以先做：
- 删除明显旧枚举/字段；
- 修正用户管理业务对象；
- 抽出 API 适配层；
- 增加权限码兼容映射。

其余页面继续保持当前可演示版本，待后端 API 稳定后切换数据源。
