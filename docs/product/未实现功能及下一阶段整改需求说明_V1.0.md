# 卫健统一门户系统—未实现功能及下一阶段整改需求说明 V1.0

> 文档日期：2026-09-20  
> 适用范围：当前 `goubeng/unified-health-portal` 项目下一阶段原型及功能整改  
> 编制依据：当前代码实现、`docs` 最新需求、2026-09-19需求修改汇总及本轮新增需求  
> 核心原则：门户权限仅管理门户自身权限；子系统业务角色、业务权限仍由子系统负责。
>
> 三层关系：**闽政通（公众用户）/ 闽政务（政务用户） → 卫健统一门户（中间层） → 各业务子系统（下层）**。
>
> “闽政通/闽政务”是身份来源；“公众用户/政务用户”是用户类别；二者均不是门户角色。门户角色只存在于统一门户中间层。

# 2. 用户、角色、组织及门户权限模块重构

## 2.1 总体权限模型

当前“门户权限配置”页面实际上主要是静态权限项列表，没有形成真正的角色权限配置闭环。

建议调整为：

```text
系统管理
├─ 用户管理
├─ 角色管理
├─ 组织管理
├─ 字典管理
└─ 配置管理
```

原独立的“门户权限配置”能力建议并入角色管理，不再单独维护一套权限页面。

统一权限关系：

```text
用户
 ↓
分配角色
 ↓
角色
 ↓
菜单权限 + 页面权限 + 操作权限 + 门户数据范围
```

用户原则上不直接逐项分配菜单权限。

## 2.2 用户管理

### 功能定位

门户只维护用户在本门户中的访问状态、所属组织索引和门户角色，不修改闽政通/闽政务的权威姓名、手机号、证件信息或密码。

### 查询条件

| 条件 | 说明 |
|---|---|
| 姓名/账号 | 模糊查询 |
| 所属组织 | 树形选择 |
| 用户类别 | 公众用户 / 政务用户 |
| 系统角色 | 按门户角色筛选 |
| 启用状态 | 启用 / 停用 |

### 列表字段

```text
序号
用户账号
姓名
用户类别
所属组织
系统角色
身份来源
启用状态
最近登录时间
操作
```

### 操作

支持：

```text
查看详情
编辑门户信息
分配角色
启用 / 停用
```

禁止：

```text
修改闽政通/闽政务姓名
修改权威手机号
修改闽政通/闽政务账号密码
给用户直接授予子系统业务权限
```

# 3. 角色管理与权限配置

当前系统角色已经支持角色名称、编码和粗粒度权限范围，但还不是完整权限模型。

角色管理增加：

| 内容 | 功能 |
|---|---|
| 基本信息 | 角色编码、角色名称、说明、启用状态 |
| 功能权限 | 菜单 / 页面 / 操作三级权限树 |
| 数据范围 | 门户自身数据访问范围 |
| 用户数量 | 当前角色关联用户数量 |
| 角色用户 | 查看已分配该角色的用户 |

建议门户数据范围支持：

```text
本人数据
本组织
本组织及下级组织
指定应用
全部门户数据
```

这里的“数据范围”只控制门户自身数据，不延伸到业务子系统。

当前数据库设计已经存在：

```text
portal_role
portal_permission
portal_role_permission
portal_user_role
portal_user_application_scope
```

因此这部分主要是把现有数据库设计真正接入页面和服务层，不一定需要新增核心权限表。

# 4. 组织管理

当前系统只有用户上的 `org_key`、`org_name`，并没有正式组织树。

本轮新增“组织管理”。

## 4.1 定位

组织主要用于：

```text
用户所属组织
角色数据范围
公告指定组织发布
管理员门户数据范围
查询与统计
```

组织不替代闽政务等上层平台的权威组织体系，可作为门户同步后的组织索引。

## 4.2 页面

采用树形组织管理：

```text
组织管理
├─ A单位
│  ├─ 业务处
│  └─ 信息处
└─ B单位
```

建议字段：

```text
组织编码
组织名称
上级组织
组织类型
组织层级
组织路径
排序
数据来源
启用状态
备注
```

需新增组织相关数据结构，例如：

```text
portal_organization
```

并与用户的 `org_key` 建立稳定关联。

# 5. 应用申请授权功能

这是当前较明显缺失的一条业务闭环。

当前只有“关联已有账号”和“进入应用”，需要增加“申请使用 / 申请授权”。

门户的“授权”仅表示门户应用入口访问资格，不代表获得子系统内部业务角色、菜单权限或数据权限。子系统最终业务权限仍由子系统控制。

## 5.1 用户端流程

```text
用户进入应用中心
        ↓
发现当前应用需要申请
        ↓
点击“申请使用”
        ↓
填写申请原因
        ↓
提交申请
        ↓
待审核
        ↓
通过 / 驳回
        ↓
通过后进行账号关联
        ↓
关联成功
        ↓
进入子系统
```

应用可以配置访问模式：

```text
DIRECT        直接进入
BIND          关联账号后进入
REQUEST       申请通过后进入
```

## 5.2 用户端申请记录

建议在应用中心增加“我的申请”。

记录字段：

```text
申请编号
申请应用
申请人
所属组织
申请原因
提交时间
申请状态
审核时间
操作
```

状态：

```text
待审核
已通过
已驳回
已撤回
已失效
```

待审核状态允许申请人撤回。

## 5.3 管理端

在“应用管理”下增加“应用访问申请”。

功能包括：

```text
待审核
已处理
全部
```

支持：

```text
查看申请
通过
驳回
查看处理记录
```

批准后只生成门户应用访问资格，不会直接创建子系统业务角色。

数据库建议新增：

```text
application_access_request
application_access_grant
```

其中申请和最终授权记录分开，避免审批历史和当前有效权限混在一起。

# 8. 公告管理功能升级

公告模块是本轮重点改造模块。

## 8.1 状态调整

现有：

```text
DRAFT
PUBLISHED
WITHDRAWN
EXPIRED
```

调整为：

```text
DRAFT       草稿
SCHEDULED   定时发布
PUBLISHED   已发布
WITHDRAWN   已撤回
EXPIRED     已失效
```

## 8.2 保存与提交分离

点击“保存”始终保存为草稿，不会自动发布。

增加“提交”。

点击提交后弹出发布设置：

```text
发布方式
○ 立即发布
○ 定时发布
```

立即发布：

```text
DRAFT → PUBLISHED
```

定时发布：

```text
DRAFT → SCHEDULED
```

到达计划发布时间后自动：

```text
SCHEDULED → PUBLISHED
```

不需要额外增加“已提交”状态。

# 9. 公告发布时间及失效时间

当前“生效时间”建议取消原来的含义，重新整理为：

```text
发布方式
计划发布时间
实际发布时间
失效时间
```

立即发布：

```text
实际发布时间 = 当前时间
计划发布时间 = 空
```

定时发布：

```text
计划发布时间 = 用户选择时间
实际发布时间 = 到时自动发布的时间
```

失效时间允许为空。

为空表示永久有效。

有值时：

```text
当前时间 >= 失效时间
```

公告自动进入 `EXPIRED`。

# 17. 系统分类调整

当前数据库已经有 `application_category.status`，但是前端编辑弹窗没有状态字段，而且保存时当前代码会直接写 `status = ENABLED`，因此这是当前明确缺陷。

编辑系统分类应增加：

```text
分类名称
分类编码
排序
启用状态
备注
```

启用状态使用TDesign Switch。

规则：

```text
停用分类：
已有应用仍可显示原分类
新增/编辑应用时不可再选择该分类
```

删除规则继续保持：有应用正在使用的分类不得删除。

如果后续系统分类正式迁移到字典管理，则逐步由 `application_category` 迁移至统一 `dict_type` / `dict_item`，迁移完成前不直接删除现有分类表，以避免破坏现有应用关联；完成数据迁移和引用切换后，独立“系统分类”维护入口退出最终信息架构。

# 18. 页面加载时先出现“暂无符合条件”问题

这是当前代码中的真实UI问题。

当前页面初始化时 `rows = []`，接口数据还没有返回，但列表和 EmptyState 已经开始渲染，因此页面会短暂出现“暂无符合条件的记录”，随后接口返回数据，又变成正常列表。

这不是数据问题，是 Loading 状态与 Empty 状态没有分开。

统一改为：

```text
未完成首次加载
→ 只显示Loading

加载成功且有数据
→ 显示列表

加载成功且确实0条
→ 显示Empty

请求失败
→ 显示错误 + 重试
```

列表页、详情页、卡片页都需要统一修复。

建议增加 `initialized / loaded` 状态，而不是通过 `rows.length === 0` 直接判断空数据。

# 21. 门户操作日志

当前“操作人 + description”的信息过于简单。

建议字段：

```text
序号
操作时间
操作人
所属组织
操作模块
操作页面
操作类型
操作对象
操作结果
操作说明
请求ID
```

例如：

```text
操作人：周明
操作模块：应用管理
操作页面：应用列表
操作类型：编辑应用
操作对象：健康档案管理系统
操作结果：成功
操作说明：修改应用基础信息
```

“查看了哪个模块、操作了哪个对象”应该由：

```text

```

生成，而不是仅保存一句“操作已记录”。

当前数据库的 `audit_event` 已经有上述字段，因此主要是服务端日志内容写得不够完整，并不是必须先改表。

列表中的“创建时间”统一更名为“操作时间”，仅修改展示名称，不改数据库 `created_at`。

# 24. 运行监控详情的“状态”字段

目前前端 `monitorProfiles()` 会额外派生一个 `status`，它实际上是把 SSO、TODO、MESSAGE 三个状态再次汇总成一个综合状态。

但当前产品已经明确运行监控按 SSO状态、TODO状态、MESSAGE状态分别展示。

因此详情页中的“状态”属于冗余信息，建议删除。

但是不要删除数据库 `monitor_status.status` 字段。

数据库中的 `monitor_status.status` 表示某一个具体服务的运行状态，例如：

```text
系统A + SSO → NORMAL
系统A + TODO → ABNORMAL
系统A + MESSAGE → NORMAL
```

这个字段本身必须保留。

需要删除的是前端聚合DTO中的 `status` 或至少不再在详情页面展示。

最终运行监控详情建议采用：

| 接入类型 | 运行状态 | 最近成功 | 最近失败 | 连续失败 | 响应时间 | 最近错误 |
|---|---|---|---|---:|---:|---|
| SSO | 正常 | — | — | 0 | — | — |
| TODO | 异常 | … | … | 2 | 1250ms | … |
| MESSAGE | 未配置 | — | — | 0 | — | — |

# 30. 后续开发使用说明

本文件作为下一阶段改造方向基线使用。

后续实施时建议优先保证：

1. 先完成权限模型、组织、应用授权申请等结构性能力；
2. 再完成公告状态机和字典管理；
3. 同步修复日志、运行监控、加载态和UI一致性；
4. 每完成一项，回写本文件或生成对应实施记录；
5. 对涉及数据库的调整必须同步更新数据字典、迁移脚本、Mock/Seed及验收测试；
6. 不得因门户权限改造而扩展为对子系统业务角色、菜单权限和数据权限的管理。
