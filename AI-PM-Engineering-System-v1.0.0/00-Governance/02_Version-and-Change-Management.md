# 版本与变更管理规范

## 1. 为什么必须做版本管理

你的工程体系会持续补充和修改；项目本身也会持续迭代。如果只有“最新版”，以后很难回答：

- 这条规则什么时候改的？
- 为什么改？
- 哪些页面受影响？
- 哪个部署包对应哪个数据库？
- 交付给开发的文档是不是和代码同一版本？

所以版本必须覆盖四个层级。

## 2. 四层版本

### A. 工程体系版本

例如：

`AI-PM-Engineering-System v1.0.0`

记录在根目录 `VERSION.md / CHANGELOG.md`。

### B. 项目版本

例如：

`公产房管理系统 v0.8.0`

开发期可以 0.x；首次正式交付可进入 1.0.0。

### C. 基线版本

例如：

`Baseline 2026-09-16-RC1`

代表一次已经通过一致性复核的设计+代码+数据库组合。

### D. 发布包版本

例如：

```text
property-system-full-v1.0.0.zip
property-system-patch-v1.0.1.zip
property-system-deploy-v1.0.1.zip
```

## 3. 推荐版本升级规则

- MAJOR：业务模型、核心流程或工程结构发生不兼容变化。
- MINOR：新增模块、页面、重要能力。
- PATCH：修复、样式调整、小字段调整、提示文案等。

## 4. 每次变更必须记录

项目 `.project/CHANGELOG.md` 至少包含：

| 字段 | 说明 |
|---|---|
| 版本 | v0.x.x |
| 日期 | YYYY-MM-DD |
| 需求/问题 | 用户提出什么 |
| 修改内容 | 改了什么 |
| 影响模块 | 哪些页面/模块 |
| 影响资产 | 状态机/数据库/消息/履历/文档等 |
| 文件范围 | 主要代码文件 |
| 数据库变更 | 有/无 |
| 兼容性 | 是否需要迁移 |
| 验证结果 | 已验证/待验证 |

## 5. 设计变更影响链

发生以下修改时必须检查关联资产：

### 状态变化

同步检查：

`状态机 → 操作矩阵 → 页面按钮 → 权限 → 消息 → 操作履历 → 测试用例`

### 字段变化

同步检查：

`数据库 → API/Service → 表单 → 列表 → 详情 → 导入导出 → 文档`

### 角色变化

同步检查：

`角色定义 → 菜单 → 操作矩阵 → 权限矩阵 → 消息接收人 → 测试`

### 业务动作变化

同步检查：

`操作矩阵 → 状态机 → 履历 → 消息 → 二次确认 → 测试`

## 6. 决策记录

对于“为什么这样设计”的重要决定，写入 `.project/DECISIONS.md`，不要只留在聊天记录中。
